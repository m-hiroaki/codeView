# 有界表示の行別投影と全文スクロールの設計変更案

状態：A-03承認済み（2026-11-06）。提案日2026-11-06。ユーザーから「設計変更案に沿って試作を進める」と回答を受けた。以下の行別投影とCaretから独立した閲覧位置を専用試作へ追加する範囲を承認済みとし、記載した移行計画・戻し方・受け入れ条件を維持する。通常UIへの採用や原文保持/レイヤ/検索・コピー契約の変更を、この承認から推定しない。行別投影の実装・検証はA-04/A-05で進める。

## 理由と現状の証拠

[可視行数比較](validation-results/2026-11-06-viewport-lines/README.md)で、通常行は15→36行を表示できたが、長行を含むとCreateViewportSliceは固定文字数窓へ戻る。DocumentDisplaySliceはSourceOffsetからText.Lengthまでの原文の連続範囲であり、位置変換は単純な足し算に依存している。例えば50 MiBの行とその前後の行を1本の連続範囲で表示するには、その50 MiBも含める必要がある。16 Ki単位の表示上限と同時には成立しない。

また現在のRenderInteractiveはCaretが窓外なら窓をCaretへ戻す。局所スクロールバーの位置だけを全文へ換算しても、選択/コピーを維持してCaretから離れた本文を閲覧できない。これは通常行対応の延長だけで解決できる問題ではない。

## 比較した選択肢

| 方式 | 利点 | 不利点・判断 |
| --- | --- | --- |
| 現在の連続窓を拡大 | 足し算の原文対応と既存の選択処理を維持 | 巨大行の全文レイアウトを再導入する。長行混在の要件を満たさないため不採用 |
| 可視行ごとに横方向の必要範囲だけ投影 | 原文の本文保持/行索引/ReadLeaseを維持し、長行と前後の行を同時に描ける | 行別の位置対応、選択投影、横・縦スクロールを接続し直す必要。まずこの方式を試作する提案 |
| AvaloniaEditを全面的な独自レンダラーへ置換 | 描画/ヒットテスト/スクロールの全責務を制御可能 | フォント、タブ、Unicode、選択、IME、アクセシビリティまで影響。行別投影の評価なしでは範囲が過大 |
| 本文をストリーミング/MMFへ変更 | 全文保持の選択肢 | 今回の描画量の問題は解決せず、文字コード/索引/検索/寿命へ影響するため今回の変更に含めない |

## 承認を求める変更範囲

既存Documents内の試作表示モデルと、専用GUIの入力/描画接続を変更する。レイヤ、プロジェクト、Contractsの位置、検索結果、元本文の保持形式、外部公開APIは変更しない。通常製品UIへの採用は別途G2判断とする。

- 連続Sliceに代えて、可視行別の原文範囲と表示範囲を持つ不変投影を試作する。各行は原文行番号、原文範囲の先頭と長さ、表示位置、左右の切詰め有無を持つ。数は画面相当の行数に限定し、全文分の一覧/索引を追加しない。
- 原文Anchor/Caretと、表示先頭の原文行/横方向の閲覧位置を別に所有する。スクロールだけでAnchor/Caret・選択範囲を変更しない。クリック/キー移動/検索ジャンプで必要になったときにだけCaretを表示範囲へ収める。
- 原文行ごとに横方向の必要範囲だけをReadLeaseから取得し、表示用文書へ並べる。表示用の行区切りは原文のCR/LF/CRLFと区別して対応付ける。原文を正規化せず、コピーは既存の原文範囲/独立Leaseから行う。局所文書のコピーを使用しない。
- 切詰めは行外の視覚的な印で示す。省略記号などの人工文字を原文として位置変換/コピーしない。サロゲート対とCRLFを分断せず、行頭/行末/EOF/空行と画面外Caretを明示的に扱う。
- 全文の縦スクロールは原文行索引に対応し、ホイール/トラックパッド/スクロールバーから表示先頭を更新する。横スクロールも表示用文字列の長さを原文の最大列と誤認しない。原文全体の最大行長が必要な場合は、UI上で全行走査せず、既存のワーカー構築中に収集する小さなメタデータの追加を比較する。その追加CPU/割当も測定する。
- 元文書/表示世代/投影インスタンスの同一性で古い入力/Loaded通知を拒否する。ポインター捕捉・自動移動・文書切替・再読込・終了の所有者を増やさず、既存の単一受付へ接続する。

表示総量の16 Ki単位は現行試作の比較条件であり、画面の行数×必要列数によっては不足する。まず同上限で行別投影を比較し、画面を満たせない場合は可視行/列から算出する上限を候補として明示して比較する。CPU・メモリ・接続100ms・tick16.7ms等の既存合格予算は変更しない。表示上限の拡大だけで未達を解消したことにしない。

## メリットとデメリット

メリットは長行の全レイアウトを避けながら前後の原文行を読めることと、検索/コピー/タブが持つ原文位置を維持できることである。既存の全文本文保持/ReadLease/行索引を再利用し、新たな永続索引・フレームワーク・バックグラウンド常駐処理は不要。

デメリットは行別の双方向位置対応、選択・水平可視化、スクロールの独立状態が必要になること。表示用文書の再構築・描画・割当・CPUコスト、フォント/タブ/絵文字/結合列/双方向テキスト、アクセシビリティ、文法の行状態を検証し直す必要がある。現段階で速度改善・採用可能とは断定しない。

## 影響範囲

| 対象 | 変更/再検証 |
| --- | --- |
| Documentsの試作表示 | 不変投影と原文/表示位置・選択の変換、閲覧位置とCaretの独立 |
| DocumentBuilder/Handle | 横スクロール範囲に必要と判断した場合のみ、最大行長等の小さな構築メタデータを比較 |
| 専用GUI | 行番号、入力、キャレット可視化、縦/横スクロール、選択描画、表示量診断 |
| Operations/検索/タブ | 原文契約は維持。コピー寿命・タブ位置/再読込/検索ジャンプは統合回帰 |
| 文法 | 原文行状態と表示部分の対応を評価。表示用の改行や省略位置を原文トークン位置と混同しない |
| テスト/設計/性能記録 | 新旧投影の比較・同じ入力/予算での証跡。従来方式の未達も保持 |

## 移行計画と戻し方

1. 承認後、試作内に新しい投影/閲覧位置の単体試験と実装を追加する。通常製品は従来方式のまま。
2. 通常行/巨大行/長行混在/改行/空/Unicodeの不変条件と、有界保持/取得コストをUIなしで確認する。
3. 専用フラグで行番号/キーボード/コピーを接続し、表示上限・位置・全選択・画面外Caretを記録する。従来の比較フラグも残す。
4. 縦/横の全文スクロール、クリック/ドラッグ/Shift/範囲外自動移動を接続する。入力による原文変化と、スクロールだけの状態変化を別々に検証する。
5. 10/50/100 MiB、50 MiB×5、通常/長行/混在、文法有無、OS差と回帰を同じ予算で評価し、A-02/A-05/P2-09/G2を判断する。未達は方式を確定しない。
6. G2の採否が成立した場合だけ通常Presentationへ移し、同じ受入を再実行する。測定専用コードを製品依存へ残さない。

採用前は専用フラグを外せば従来試作/通常製品へ戻る。元本文・設定・ソースの保存形式を変えないのでデータ移行は不要。採用後の戻し方は移行差分を戻し、元の性能未達を再掲する。未達入力を拒否して回復扱いにはしない。

## 完了を証明する検証

- 正常/逆方向選択、行/文頭末尾、空行/末尾改行、CR/LF/CRLF、日本語/サロゲート、境界を含む原文/表示の往復が正しい。無効入力や古い/他の投影が現在の状態を変えない。
- 1行50 MiBと多数の長行混在でも、可視行数を満たし、行番号/原文ステータス/検索位置/コピーが一致する。表示窓の総量・行数が文書全長で増えない。
- Caretを画面外へ残して全文を縦/横へ移動できる。スクロールだけでは選択範囲とコピー内容が変わらず、次の原文入力で正しい位置へ復帰する。
- 連続ドラッグ/範囲外移動/窓交換/捕捉喪失/タブ切替/再読込/検索/終了で再帰・後着採用・資源残留がない。
- 同一入力/固定ビルドのCPU・割当・メモリ・GC・接続/描画・起動/検索回帰が既存予算を満たす。未測定/単発差は合格の代用にしない。

A-03のチェックはユーザー承認後に更新する。承認待ちを理由に独立した準備・起動/例外境界の共通検証まで停止しない。
