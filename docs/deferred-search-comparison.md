# 非表示検索パネルの遅延構築候補

A-01-04。前段の[起動12段階](validation-results/2026-11-06-startup-stages/README.md)ではウィンドウXAML読込が最大区間（中央値354〜365 ms）だった。起動時に非表示の検索コントロール群を構築しない候補を、同じホスト上で比較する。測定前の条件をここに固定する。比較後に採否と原記録を追記する。

## 候補と影響

MainWindow内の検索パネルを既存のAvalonia DataTemplateへ移し、最初のIsVisible=trueで一度だけBuildする。MainWindowのprivate Lazyがそのウィンドウのコントロールを保持し、以降は表示を切り替える。テンプレートの名前スコープで結果Enterのイベントを接続し、検索語へのFocusも同じスコープから取得する。ClosedでViewModelの表示通知を解除する。

層・モジュール・依存方向・公開API・検索/本文モデル・設定保存は変更しない。UI構築時期だけの候補であり、承認済みの行別投影の専用試作とは別の変更である。利点は起動時のコントロール構築とJITの削減が見込めること。不利点は初回検索表示へコストが移り、名前スコープ/イベント接続/Focusの回帰が必要になること。効果を確認するまで通常採用の完了とはしない。未達なら候補2ファイルを戻し、比較器・原差分・結果は保持する。

## 測定と採否条件

[Deferred search startup comparison](../.github/workflows/startup-comparison.yml)はWindows/macOSそれぞれ同じホストで、94bbefdの変更前と候補をReleaseの明示診断としてビルドする。SDK・依存・入力を共有し、起動は変更前→候補、次の回は候補→変更前の順で交互に各10回実行する。各起動の空/ファイルを含め、各OS40プロセスである。既存収集器でコミット/全文表示候補/12段階/入力SHA/本文文字数/64スクロール/終了0を判定する。Cold・通常AOT・物理描画の比較ではない。

候補の機能確認は別3プロセスで行う。実Window/テンプレートで、初期未構築、初回メニュー表示とQuery/Focus、TwoWay Binding、正規表現の不正式、正常語の1確定結果、結果Enterで既存タブ/本文選択/Focus、表示3反復で同じコントロール/条件/結果を保持、クリア、空語の検索無効、本文/入力SHA不変を確認する。結果Enterはそのイベントだけを診断ガードから除外するRoutedイベントで、OSキーを注入しない。検索対象は生成した入力1ファイルだけのフォルダである。

採用には両OSで次をすべて求める。

- 空/ファイルのMain→Opened中央値がそれぞれ5%以上短縮する。
- 各条件のCPU・OSメモリの中央値増加がそれぞれ5%以内。
- 初回検索表示の同期処理が3回すべて100 ms以内。2通知到達も別に記録し、物理描画完了とは扱わない。
- 機能条件すべてが成功し、通常試験・既存実GUI・Windows AOTの回帰が成功する。

起動を速くして初回操作を重くした候補は採用しない。1秒の実起動目標・100 ms接続・本文性能等の既存予算も緩めない。相対比較で採用できてもG1/G2や実機の物理描画/入力を合格にはしない。

比較器は取得成立とcandidateAcceptedを区別し、性能不採用でも全取得後に非0を返す。機能失敗/期限切れは再実行せず、その時点のJSON/ログを保存する。名前スコープやBindingはUI依存のため実OS結合試験で確認し、異常/空の検索、共有例外境界は既存単体でも検証する。比較器の7ケースは採否の境界・取得失敗・期限・交互順序・機能成功と性能失敗の分離を単体で検証する。

通常のCIに加えて比較ワークフローを実行する。比較ワークフローはこの候補の評価用であり、候補を戻した後の通常製品に対して未構築を要求する受入ゲートではない。再現時は候補コミットを含むブランチでワークフローを実行する。原記録のActions artifactは14日保存する。
