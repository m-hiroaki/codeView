# 04 本文・タブ・表示

[索引](README.md) / 関連：[ファイル読込](03-files-tree.md)、[検索](05-search.md) / 上位：基本設計4.3・4.4、アーキテクチャ設計5.1・7章

## 1. 本文ライブラリ境界

| 型・配置 | 操作 | 契約 |
| --- | --- | --- |
| `IDocumentAdapter` / Documents | `CreateBuilder`、`AcquireReadView(document)`、`Attach`、`Detach`、`MoveTo`、`Release` | ライブラリ非依存の構築器・文書ハンドル・位置を入口にする。UI型は表示側の具体接続に閉じる |
| `DocumentBuilder` / Documents | `Append(chunk)`、`Complete`、`Release` | 未接続文書を構築する。Filesの型やストリームを受け取らない |
| `AvaloniaEditDocumentAdapter` / Documents | 上記の初期候補実装 | Phase 2採否待ち。本文生成・所有移譲・読取ビュー・位置変換を局所化 |
| `DocumentHandle` / Documents | 文書版、長さ、行数、非公開の具体文書参照 | タブが所有。借用中の読取ビュー数を追跡する |
| `DocumentReadLease` / Documents | `ReadRange`または逐次読取、長さ・版、`Dispose` | ワーカーが読める不変ビュー。全文文字列へ変換しない |
| `TabState` / Operations | 下記タブ状態 | 表示文書ハンドルの唯一の所有者 |

Operationsの読込処理がFileReaderからのチャンクをDocumentBuilderへ渡し、Completeの成功でDocumentHandleを得る。DocumentsからFilesへ、FilesからDocumentsへ直接依存しない。具体文書型、TextMate接続、キャレット・スクロールAPIはDocumentsと表示側以外へ出さない。新しい汎用テキストモデルやDocumentNavigatorの独立モジュールは作らない。責務分離はアーキテクチャ5.1の条件で後に評価する。

## 2. 構築・接続・読取ビュー

Phase 2の試作候補は、非表示の文書をワーカー上で構築し、構築が成功してからUIへ接続する方式とする。構築中は借用チャンクを文書へ取り込み、元チャンクの全文コピーを別途残さない。読込に伴うUndo履歴を残さない設定・初期化手順も確認する。

本文構築は、準備後に1つのバックグラウンド実行区間でBuilderを作り、FileReaderの同期ReadChunksからAppendを呼び、Complete・所有解放までを同じスレッド上で行う案とする。同期I/OはUIへ持ち込まない。文書所有中にawaitで任意のスレッドへ移る構造にせず、チャンク間で取消を確認する。検索では文書を構築しないので非同期ReadChunksAsyncを利用できる。

DocumentBuilder.Appendは借用チャンクだけを一時文字列化し、既存TextDocumentへ挿入する。Append後のデコーダー配列再利用で原文を変えない。RopeTextSource経由のコピー削減も比較したが、割当減に対して時間/CPU増とGC予算未達が残ったため採用せず、この通常経路を維持する。[コピー削減の不採用根拠・回帰](../validation-results/2026-11-06-document-copy/README.md)。保持形式・型・所有/ReadLease・Undo無効化・構築枠は変更しない。

AvaloniaEditの現行ソースには所有スレッドの移譲と不変スナップショット取得がある。ただし採用版の契約とコストを確認するまで、具体APIを前提に実装を確定しない。参照：[TextDocumentの一次ソース](https://raw.githubusercontent.com/AvaloniaUI/AvaloniaEdit/master/src/AvaloniaEdit/Document/TextDocument.cs)。

検証順は次のとおり。

1. ワーカーが文書を構築し、構築完了後にワーカーからアクセスできない状態へ移す。
2. UIで世代を検証し、所有スレッドを引き継いで接続する。移譲できない場合は、不変の中間表現のまま受け渡す案を評価し、全文複製のピークを測る。
3. 文書版に対応する読取ビューを作り、バックグラウンド検索が安全に利用できるか検証する。
4. 検索ごとに全文コピーが生じないこと、ビュー解放後に旧本文が残らないことを測定する。
5. UI上の文書接続と初回レイアウトが100ms超の停止を起こさないか確認する。

上記が成立しない場合はD-02未完了とし、UIスレッド上で巨大な全文構築を行って解決済みにしない。独自仮想表示・ストリーミング・MemoryMappedFileの比較へ進む場合は上位設計の変更手順に従う。

読取ビューが使用中の文書を閉じた場合、UI・タブの参照は直ちに外して検索を取消する。最後のLeaseが解放されてから本文資源を解放する。遅い検索を理由に旧本文を無期限にキャッシュしない。

初期実装は`DocumentBuilder`の同一スレッドAppend→Complete→所有解放と、表示側のClaimForDisplayで接続する。Undoのサイズを0にし、完了時に履歴をクリアする。ReadLeaseは不変スナップショットを持ち、閉鎖時にライブ文書を切り離しても使用中のスナップショットだけをLease解放まで保持する。小ファイルの移譲と寿命を単体試験した段階であり、スナップショットの割当量・大量タブの性能はD-02で別に実測する。

`DocumentReadLease.VisitChunks(consume, ct)`は呼出元のワーカー上で不変ビューのTextReaderを開き、最大16 Ki UTF-16単位の借用メモリを順に返す。実際の長さはreaderに依存し、末尾以外も短いチャンクを返せる。利用側は固定長を前提にしない。コールバックがfalseを返すとそのチャンクで終了し、返却値は最後のチャンクを含む配信文字数とする。各呼出は先頭から独立して読む。検索位置の計算・正規化・照合はこの読取境界で行わず、利用側がCRLFやサロゲートの持越しを処理する。

借用メモリはコールバック内でだけ有効で、保持やawaitをしない。取消は読取前・通知前・通知後に確認し、コールバック内の取消も終了前に観測する。falseは通常の早期終了であり取消とは区別する。利用側の例外は変換せず伝播し、readerは正常・早期終了・取消・例外で破棄する。走査中は取得済みLeaseを利用側が保持し、同じLeaseのDisposeと操作を競合させない。文書本体を閉じても既存Leaseの不変ビューは読めるが、Lease破棄後の新しい走査はできない。

## 3. タブの状態と遷移

`TabState`はTabId、指定パス、LoadEpoch、DocumentVersion、EncodingChoice、DocumentHandle、SourceStamp、カーソル・表示位置、本文内検索状態を持つ。表示名やツールチップ文言はTabViewModelで作る。

| 現状態 | 操作・結果 | 次状態・処理 |
| --- | --- | --- |
| 未作成 | Open | `Loading`のタブを作り読込枠へ |
| Loading | 成功・採用条件一致 | `Ready`、DocumentVersionを進めて本文所有を移譲 |
| Loading | 失敗 | `Failed`、理由・文字コード指定・再試行を表示 |
| Loading | 閉じる | `Closed`、世代無効化・取消。後着の文書は破棄 |
| Ready | 再読込・文字コード変更 | `Reloading`、旧本文を読めるまま新世代で開始 |
| Reloading | 成功 | `Ready`、新本文へ一度だけ入替。旧Leaseの終了後に旧本文破棄 |
| Reloading | 失敗・明示取消 | `Ready`、旧本文・版・文字コードを維持して通知 |
| Failed | 再試行 | 新LoadEpochの`Loading` |
| Ready / Reloading / Failed | 閉じる | `Closed`、関連要求・購読・文法接続を解放 |

同一指定パスのタブがあればそのタブを選択し、重複読込を始めない。読込前の同時Openも予約済みパスを見て統合する。別パスの同名ファイルは別タブとし、親パスで区別する。0タブは空画面、タブ切替でフォーカスと表示位置を復元する。

### 3.1 タブ状態の実装境界と移行

Operations内のTabManagerがTabState一覧、正規化指定パスのOrdinal辞書、ActiveTab、タブ別要求、FIFO待機列を所有する。TabStateはId、Path、LoadEpoch、DocumentVersion、Status、LoadedFile（文書ハンドル/Stamp/文字コード名）、最後に成功したEncodingChoice、Error、取消状態、TextPositionと水平/垂直オフセットを持つ。本文内検索・保留移動は後続機能の接続時に追加し、未実装の検索状態を生成しない。具体的なTextDocument/View型は持たない。

OpenAsyncは受付時にパスを予約してタブを追加/選択する。予約済みタブに要求があれば同じTaskを返し、Readyなら再読込せず選択だけを行う。Failedを再度Openしても自動再試行せず、明示ReloadAsync/文字コード指定で再試行する。異なるパスはファイル名が同じでも統合しない。未確認のファイル同一性・大小文字別名は従来のパス方針に従う。

待機列は既定256要求以下で、実行中は1要求。上限は共通Openの256パス予算に対応する内部の保護上限で、設定項目を増やさない。新規要求の上限超過はタブを作成/選択せずQueueFull。待機中の同タブ再読込は旧待機を除去して末尾へ置き、旧Taskを取消結果で完了する。閉鎖した待機も直ちに除去する。実行中の取消不能処理は完了まで共有本文枠を保持し、後続要求が先にI/Oを始めない。

ワーカーが返した新文書は、所有タブの存在・LoadEpoch・取消・受付終了を確認してから採用する。不採用や採用前の例外ではfinallyで新文書を解放する。成功した採用だけがDocumentVersionを進め、旧文書のライブ参照を外す。旧Leaseは自身の不変ビューを解放まで保持する。失敗/取消で旧本文があればReadyと旧本文/版/文字コードを保持し、本文がなければFailedと理由/取消状態を示す。バックグラウンド完了はActiveTabを変更しない。

SelectとSaveViewは生存タブだけを対象とし、スクロールは有限の非負値、位置は1始まりを保存する。新本文に対する位置・スクロールの有効範囲への補正は表示アダプター側で行う。アクティブタブ閉鎖時は右隣、右隣がなければ左隣を選び、最後のタブを閉じるとActiveTabはnull。未知の読込例外は要求TaskとPendingWorkで観測し、以後の受付を止めてUIの致命的終了へ渡す。閉鎖/終了で全タブを解放するが、取消不能I/Oの終了待ちを同期的に行わない。

ノード・ルート管理が増えたAppOperationsへタブ辞書/列/寿命まで集中させないため、TabManagerを同じOperations内に置く。理由は責務集中の回避、利点は文書所有と順序をUIなしで検証できること、不利点は表示選択/終了待ちの接続点が増えること。影響はOperations内のタブ状態とPresentationの終了待ちで、層・依存方向・Contracts・本文候補を変えない。

通常UIのOpen/再読込/文字コード指定/閉鎖をAppOperations.Tabsへ統一した。ワーカーの文書構築はBuildDocumentを再利用し、本文枠1で行う。AppOperationsの単体ファイル用のLoadEpoch/取消/本文所有状態は削除し、CurrentFile/OpenFileAsync/CloseFileはActiveTabを参照する薄い入口として残す。内部状態/寿命試験→通常UI統一→タブヘッダー/表示位置/アクティブView接続→旧単体状態削除までは反映済みで、性能・実機検証が残る。G2の未採用本文モデルへ最終固定せず、本文候補を替える場合は同じ構築結果/ハンドル境界と寿命試験で再検証する。

### 3.2 通常UIへの接続

PresentationのTabViewModelはTabStateへの参照とラベル/読込状態を持ち、同名ファイルは親パスを追加して区別する。横方向の仮想化ListBoxにヘッダーと閉鎖ボタンを表示する。選択・閉鎖・Ctrl+Tab/Ctrl+Shift+Tab、Ctrl/Cmd+WをTabManagerへ渡し、Loading/Failedでも閉鎖・再試行を可能にする。選択同期中のバインディング通知から再度Selectを呼ばず、背景タブの完了で現在の選択/本文を上書きしない。

MainWindowViewModelは表示中タブと表示ハンドルを参照し、選択タブ/文書が変わった時だけClaimForDisplayを行う。同じReadyタブの再Openや他タブの閉鎖では本文を再構築/再接続しない。本文Viewは共通の1個だけを使う。失敗パスと文字コードのグローバル状態は削除し、選択タブの状態を使う。位置・スクロールのイベントは表示中タブへ保存し、文書バインド中の初期化イベントは保存へ反映しない。

文書接続後に保存位置を行数/行長へ補正し、カーソルを戻す。スクロールはLoaded優先度で保存値を戻し、表示世代ViewEpochが変わっていれば古い復元を破棄する。採用候補12.0.0のScrollToHorizontalOffset/ScrollToVerticalOffsetは処理が未実装のため使用せず、公開IScrollable.Offsetへ現在のExtent/Viewport内に収めた値を設定する。位置とスクロールの計算/世代/通知は単体検証し、実際のレイアウト・フォーカス・遅延復元の挙動は実機で別に確認する。参照：[TextEditor](https://github.com/AvaloniaUI/AvaloniaEdit/blob/12.0.0/src/AvaloniaEdit/TextEditor.cs)、[TextView](https://github.com/AvaloniaUI/AvaloniaEdit/blob/12.0.0/src/AvaloniaEdit/Rendering/TextView.cs)。

この接続は既存の設計済みタブ所有へUIを移すもので、層・依存方向・本文ハンドル契約を変えない。利点はパス/文字コード/位置/本文寿命の二重管理を解消できること、不利点は単体表示より保持文書が増え、切替時の実機性能と購読/文法の解放検証が必要になること。影響はOperationsの入口、Presentation、旧単体操作の試験と利用手順に限定する。実GUI・5本文保持・長時間試験が済むまではP3-04/P3-05/G3を完了としない。

## 4. 表示・読み取り専用

- 本文コントロールは読み取り専用にし、編集・保存・Undo/Redo・整形のコマンドを接続しない。入力、貼付、本文へのドロップ挿入を禁止する。
- 選択、コピー、カーソル移動、行番号、横・縦スクロールを利用できるようにする。折り返しは初期無効。
- アクティブタブだけに本文Viewを接続する。タブ切替時は旧カーソル・スクロールを保存し、文法・表示イベントを切り離して新タブを接続する。
- 行描画の仮想化と本文の全文保持を別に計測する。表示していない本文の追加レンダリングやタイマー処理を走らせない。
- 本文を初期化する内部書込処理はDocuments内に限り、接続後のユーザー操作から到達できないようにする。ソース書込は行わない。

## 5. 構文ハイライト

| 拡張子 | 初期対応案 |
| --- | --- |
| `.cs` | C# |
| `.c` | C |
| `.cpp` | C++ |
| `.h` | C++文法によるヘッダー表示 |
| `.json` | JSON |
| `.xml`、`.config`、`.csproj`、`.props`、`.targets` | XML |
| `.xaml` | XAML文法が同梱可能ならXAML、なければXML |
| `.md`、`.markdown` | Markdown |
| その他 | プレーンテキスト |

`.h`はC / C++で共用されるため、初期版ではC++文法に固定する。C文法との自動切替、内容解析、周辺ファイルの走査、言語選択UIは追加しない。C用ヘッダーをC++文法で表示する場合の色分け差は代表データで確認する。

文法と固定ダーク用の色設定は配布物に含める。拡張子から決めるだけにし、言語サーバーやオンライン取得を行わない。初回利用言語の文法を遅延初期化し、タブ固有のトークン状態と共有文法データの寿命を分ける。

文法読込失敗、長行・大容量で予算を超える場合はプレーン表示へ落とす。閾値はD-03の実測で決め、通知に理由を示す。本文閲覧・行番号・検索は維持する。文法処理の停止後も旧セッションが文書を保持しないことを確認する。

### Phase 2の候補と検証状況

初期候補をAvaloniaEdit.TextMate 12.0.0 / TextMateSharp.Grammars 2.0.3に固定した。DocumentsのBundledGrammarsは拡張子からスコープを決め、同梱のDarkPlusテーマ・文法をIRegistryOptionsで提供する。生成と未知拡張子の判定だけでは資源を初期化せず、資源要求の初回にRegistryOptionsを生成する。XAMLはXML文法へフォールバックする。これは候補の同梱・字句分類の検証であり、UIでの有効化・採用確定ではない。

上流RegistryOptionsの初期化は、利用言語にかかわらず同梱言語のメタデータ・設定・スニペットを読む。実際の文法読込は必要時だが、初回のメタデータ生成も起動UI上に置かず、遅延する初期化処理として測る。初回利用文法のロード・正規表現初期化と分けて計測する。

初回コア評価で、6言語を1つのRegistryへ順次ロードした前後のOSメモリ増分は71.5 MiBとなり、[初期文法予算](../performance-plan.md#7-文法候補の初期化測定)の64 MiBを超えた。GC未回収の一時割当・JIT・ネイティブ領域も含むため、この値を文法オブジェクトだけのサイズやリークとは断定しない。ただし全コンパイル済み文法を共有保持する方式は現段階で採用しない。共有するメタデータと、アクティブ表示の文法Registry・行トークンを分け、表示切替時の停止・解放、反復時のGC圧力と予算を比較する。通常表示への接続と無効化閾値は引き続きD-03未完了である。

## 6. 移動と外部更新

`MoveTo(documentVersion, position, expectedRange)`は版を確認し、行・列を有効範囲へ変換する。既に開いている結果対象はそのタブを利用し、未読込なら読込完了に対して「保留移動1件」を持つ。同タブへの新しい移動要求は古い保留移動を置換する。

結果のStamp・現在のStamp・タブのStampが異なる場合は古い可能性を通知し、明示再読込・再検索を案内する。自動監視・フォーカス時再読込・ポーリングは行わない。位置が範囲外なら末尾の有効位置へ移り、古い結果を通知する。一致文字列が違えば選択ハイライトを行わない。

一致が200文字を超える場合、結果レコードは全文を保持しない。結果の小さな照合用プレフィックスと一致長・Stampで補助確認し、厳密な全一致を再確認できない場合は自動で正確な選択範囲と断定せず再検索を案内する。ファイル更新を完全に検出できるとは扱わない。

再読込成功時はDocumentVersionを進め、本文内検索の位置・走査済み区間を無効化して同じ条件で再検索する。以前の表示位置は有効範囲に収めて復元する。共用結果は自動で最新扱いにせず、既存結果が古い可能性を残す。

文字コード指定はステータスバーとファイルメニューから同じ要求入口を使う。自動判定・UTF-8・CP932・UTF-16 LE/BE・UTF-32 LE/BEを選べる。BOMに反する指定は失敗し、成功するまで旧本文と旧指定を維持する。通常の再読込は最後に成功したEncodingChoiceを使い、自動判定へ戻す場合は利用者が明示選択する。表示名はLE/BEとCP932を区別する。

現在は失敗パス・成功した文字コード・表示位置をTabStateへ保持し、選択タブの失敗/再試行と結び付ける。本文がないFailedタブでも文字コード指定を許可し、他タブの表示設定を変更しない。カーソルは成功時に行数と行長の範囲へ補正して接続後に復元する。スクロールも表示接続へ渡すが、厳密なレイアウト後の復元は実機検証待ちである。

### 6.1 共用検索結果からの移動の実装

Presentationは現在の確定行だけを受け付け、OperationsのSearchResultNavigatorへ検索操作とSearchHitを渡す。NavigatorはTabManager.OpenAsyncで既存タブ/進行中の読込を再利用し、本文を再生成しない。FileReader.CheckStampAsyncはワーカーで現在のメタデータだけを取得する。読取・権限・存在エラーは既存のOperationErrorへ分類し、未知例外は伝播する。成功時だけ検索Stamp・現在Stamp・タブStampを照合してDocumentsへ渡す。

DocumentNavigation.Resolveは表示モデルの行索引で位置を求め、原文Offset/行列/末尾範囲とサロゲート境界を確認する。照合用の原文プレフィックスだけを最大200単位で取得し、全文や長い一致をコピーしない。Stamp不一致、位置不一致、内容不一致では選択長を0とする。範囲外は有効な行末/本文末尾へ、サロゲート途中は直前の境界へ収める。全一致を保持できない長い結果も選択せず再検索を案内する。0文字一致は有効な境界への移動とする。64bit位置を先に有効範囲へ収め、表示モデルで表せない変換はUnsupportedSizeへ分類する。同じStampで内容が書き換えられた場合の補助確認はできるが、Stamp/短いプレフィックスで全更新を検出できるとはしない。

Navigatorの実行は全体で1件、待機は最新1件に具体化する。同タブの保留1件に加えて、旧タブへの移動が後から現在表示を奪うことを避けるためである。置換待機はStarted=null/Completion=Cancelledを即時確定する。実行中は読込/メタデータTaskの実終了まで追跡し、取消不能I/Oを理由にワーカーを重ねない。取消された移動が開始したタブ読込は、独立したOpenとして維持し勝手にタブを閉じない。利点は要求とI/Oの増加を防ぎ、古い位置の不採用を1か所で試験できること。欠点は新しい他タブへの移動も旧I/Oの終了待ちになること。この間は待機表示を出し、通常のタブ切替/読書は維持する。

TabManagerにSelectionEpochを追加し、Openによる選択・明示選択・アクティブタブ閉鎖で進める。同じタブへ戻る操作も検出する。メタデータ待機後と表示直前に、検索のWorkspaceEpoch/SearchEpoch、移動要求の同一性、TabId相当のオブジェクト同一性、SelectionEpoch/LoadEpoch/DocumentVersion/Readyを確認する。位置の保存/選択は最後の採用確認後にPresentationが行い、Operationsの計算完了だけで本文位置を変更しない。後着の失敗もTask/終了待ちへ伝え、新しい待機を実行して回復したことにはしない。

MainWindowはキー/ポインター/ホイール操作を数え、待機中に新しい入力が来たら古い移動を適用しない。選択とスクロールはLoaded優先度でレイアウト後に適用し、ViewEpoch・結果の現世代・移動/タブの版・入力世代をもう一度確認する。移動時にViewEpochを進め、文書接続時の遅いviewport復元が移動先を上書きしないようにする。フォーカスはTextAreaへ渡す。結果一覧のEnterはトンネルで受け、ダブルクリックは実際の結果行から発生した場合だけ処理する。

影響はDocumentsの位置/短い照合、Filesのメタデータ入口、Operations内の移動所有者/選択世代、Presentationの結果操作/遅延適用/終了待ちに限定する。新レイヤや外部依存は追加しない。位置/Unicode単体→操作の競合→通常画面→macOSの小さい生成入力で受入確認までは実施済み。[実画面の記録](../validation-results/2026-10-31-result-navigation/README.md)。大容量/長行、Windows、IME/連続操作と他の未完了ゲートをこの確認から合格にしない。

### 6.2 有界表示の原文座標・選択・コピー基盤（統合途中）

全文接続の長行未達を受け、Documents内に`DocumentDisplaySession`を追加した。理由は、表示用の短い文書へ入れ替えるたびにAvaloniaEditの局所座標へ選択を移してしまうと、原文範囲・全選択・コピーが成立しないためである。利点は元のAnchor/Caretを表示窓と独立に保持できること、不利点はライブラリ標準の選択/スクロールと原文座標の対応を表示側で接続する必要があること。層・モジュール・依存方向は維持し、Contracts/Operationsへ表示窓の座標を追加しない。

- セッションは作成元UIスレッドで操作し、元の読み取り専用文書とReadLeaseを保持する。Anchor/Caretは原文の0起点UTF-16オフセット、ステータス位置は原文の1起点行列である。表示文書を構築しても選択をリセットしない。逆方向選択もAnchor/Caretを区別して保持する。
- `CreateSlice(target, maxChars)`は比較上限16,384単位以内の範囲と、原文先頭Offset/行列/目標位置を返す。端とキャレットがサロゲート対・CRLFの途中なら直前/直後の有効境界へ補正する。結合列や双方向レイアウトの保証ではない。元データや原文の行長へこの上限を適用しない。
- 局所イベントの採用は最新のSliceインスタンスとの同一性で確認する。同じ値で作り直した古いSlice、他セッション、レコードの複製を拒否する。無効な新要求は現在のSliceや選択を変更しない。UI接続時は既存のViewEpoch/入力世代/LoadEpochも引き続き検証する。
- `BeginCopy`はその時点の原文選択範囲と独立ReadLeaseを固定した`DocumentSelectionCopy`を返す。以後の選択変更・表示セッションの破棄・元ハンドル解放後も、その原文範囲を読み出せる。呼出側がワーカーで`WriteTo`し、必ずDisposeする。セッションのDisposeは表示Leaseと元文書参照を破棄し、タブ所有ハンドル自体は解放しない。
- `DocumentReadLease.CopyRangeTo`は範囲Readerと最大16,384単位のプールバッファでTextWriterへコピーする。本文全域の中間文字列を生成せず、CRLFや文字内容を変換しない。読み書き前後で取消を確認し、異常時もReader/バッファを返す。出力先は閉じない。同期Write内の取消不能I/Oは強制終了できず、途中まで出力済みの場合もあるため、OSクリップボード採用はコピー成功後に行う。

移行は、原文モデルとコピーの単体/性能試験→専用GUI試作の表示切出し経路→原文の行番号/ステータス/移動/スクロール→マウス/キー選択とコピー要求の寿命/クリップボード→文法/通常改行回帰の順とする。現在は専用試作で選択表示/原文キー操作/原文ステータスまで接続した。コピー受付/最終文字列/OS接続は6.5の専用試作まで進めた。原文行番号/全面仮想スクロール/可視行数とマウス選択の包括受入は未完了（6.6の専用試作では基本ドラッグまで接続）。通常製品UIではこのセッションをまだ生成しない。採用前は計測フラグを外せば従来候補へ戻せ、原文ハンドルや設定移行は不要である。

### 6.3 原文移動と選択の可視部分への変換（統合途中）

DocumentDisplaySessionは、表示Sliceの範囲に依存せず左右・論理行の移動、行頭末尾・文頭末尾への移動を行う。左右はUTF-16のサロゲート対とCRLFを1単位としてまたぎ、非拡張の左右は既存選択の指定方向の端へ畳む。これは結合列/双方向表示における視覚的な矢印移動の完成ではない。行移動は希望する原文UTF-16列を記憶して短い行では行末へ収め、次の長い行で復元する。左右/明示位置/選択/行頭末尾は希望列をリセットする。行数差は64bitで計算して有効な論理行へ収める。

TryGetDisplaySelectionは最新Sliceだけを受け付け、原文選択の表示Slice内のStart/Length、方向、切詰め有無、Slice内Caretを返す。ここで可視部分はSliceとの交差を指し、ピクセル単位の可視領域/クリッピングは表示側が扱う。CaretがSlice外ならnullとし、窓の端にあると偽らない。原文Anchor/Caretは変更しない。表示側は可視部分だけを実エディターへSelectし、原文全体の範囲はコピー/後続移動用に維持する。局所選択から原文の範囲を逆算し直して失う実装を避ける。

専用GUIの選択シナリオでは64ステップの文頭末尾/逆方向全選択/全選択/窓をまたぐ拡張を実行し、各ステップで実エディターのSelectionStart/Length/Caretを変換結果と照合する。最終の可視選択色は実画面でも確認した。これはプログラムからの原文コマンドであり、物理キー/ポインターの入力、原文の行番号/ステータス/タブ位置・スクロールバー、OSクリップボードへの接続は未完了。選択表示までは進んだが、通常UIへの採用ゲートは維持する。

### 6.4 対話キー接続とキャレットの可視化（専用試作）

原文キー操作は表示用の局所文書へ任せず、Documentsの原文モデルへ適用してから選択の交差部分を再投影する。短い表示窓で移動が止まることや局所列を原文のタブ位置として保存することを防ぐためである。専用キー割当でShift拡張、論理行/行頭末尾/文頭末尾、全選択/解除を区別する。未接続の単語移動を局所文書へフォールバックせず、試作中は診断表示にする。コピーは6.5の原文範囲を使う。これは製品機能を削る方針ではない。

表示窓内は表示文書を再利用し、余白を越えると原文Caret周辺へ窓を切り替える。入力/初期描画の購読は文書切替時に解除し、旧初期描画は世代で除外する。レイアウト後のキャレット可視化は待機1件へ集約し、実行時に最新モデル/窓の状態だけを読む。旧本文を通知に保持しない。原文ステータス/復元位置/検索移動は原文モデルへ渡し、通常の局所ピクセルOffset復元はこの試作で使わない。全面スクロール座標やタブ/再読込の包括受入が残るため通常UIへ採用しない。

12.0.0のScrollToは横方向目標を0へ戻すため、キャレット可視化はEnsureVisualLines後にCaret.BringCaretToViewで行い、矩形/Viewport/Offsetと実画面で確認する。通常UIの結果移動も、既存Loaded/世代/入力検証の後に同APIへ40 DIPの文脈余白を与えて一致先頭が右端へ隠れないようにした。縦方向の既存位置決めは維持する。大きな一致全体を常に可視領域へ収める保証ではない。[ソースと実画面の検証記録](../validation-results/2026-10-31-bounded-keyboard/README.md)を参照する。過去のScrollTo同期時間だけを正しい水平位置の可視化証明にしない。

試作コードは計測用ビルドへ限定し、採用時に入力/描画の責務をPresentationの表示部へ移し、計測器を製品依存へ残さない。利点は原文モデル/層/依存を維持して実キーを比較できること、不利点は計測器内の接続が増え、移行時の再検証が必要なこと。当初のマウスクリックはフォーカスのみだったが、6.6で専用試作の原文ドラッグを接続した。既知の選択中再帰障害の修正や、コピーの包括受入/IME/結合列/双方向/別OSの受入完了とは扱わない。

### 6.5 原文コピーの受付とクリップボード（専用試作）

短い表示文書の標準コピーでは原文選択を失うため、Operations内のClipboardCopyCoordinatorがBeginCopyの独立Leaseと要求寿命を所有する。UI所有スレッドで受付・取消・採用を行い、実行1件と最新待機1件に制限する。文字列準備はワーカー、OS接続はUIへ戻して行う。新要求は旧要求を取消し、置換された待機は即時にLeaseを解放する。実行枠は準備/OS書込みの実終了まで保持する。空選択は非変更とし、旧要求も置換しない。

選択やキャレットが動いても、押下時点の原文範囲をコピーする。文書切替/閉鎖/終了は要求を無効化する。準備終了後とOS書込み直前に現要求を確認するが、開始したOS書込みを取消・ロールバックすることはできない。結果のWriteStartedで開始有無を残し、旧書込みの終了後に最新要求を書込む。同じ所有者への原文コピーだけを直列化し、他アプリや別UI経路の変更との全体排他は保証しない。

ReadRangeAsStringはstring.Createで最終文字列を1つ確保し、最大16 Ki単位のプールバッファから埋める。全文サイズの中間StringBuilder/文字列は作らず、バッファを消去して返す。原文を正規化・改行変換しない。準備成功後はOS呼出し前にLeaseを解放し、要求結果は件数/状態だけを保持する。大きな最終文字列とOS側の複製コストは残る。長さ不一致や未知例外、無関係な取消は失敗として受付を停止し、要求TaskとPendingWorkで観測する。

専用GUIは初回コピー時に所有者を生成し、SetValueAsync(DataFormat.Text)→FlushAsyncをUIで実行する。利用不能と既知の可用性エラーはUnavailableとして通知し再試行を許す。SEHを含む未知障害は致命的経路へ渡す。UI通知は単一の監視Taskで最新要求/表示世代だけを採用し、コピーごとの継続Taskを増やさない。終了は[02の8章](02-runtime-ui.md#8-例外境界と終了)の上限待ちへ含める。

利点は本文範囲とOS接続を分離して競合/寿命を単体検証でき、連打でも全文割当やOS書込みを重ねないこと。欠点は取消不能な旧OS処理が最新要求を待たせ、最終文字列の割当が必要なこと。影響はDocumentsの範囲読取、Operations内のコピー所有者、専用GUIと終了待ちだけで、新レイヤ/外部依存/ContractsのUI型は追加しない。移行は単体・文字列性能→専用GUI→通常採用時にアプリ全体で所有者を共有し、OS接続をPresentationへ移す順とする。現在は専用試作のみで、通常UIの標準コピーは置換していない。

[検証記録](../validation-results/2026-10-31-source-clipboard/README.md)：通常558件、50 MiBの文字列準備3件と小さい入力のmacOS読戻し3回が合格。大容量OS転送、Windows、終了後保持、実機での書込み中取消/長時間利用は未検証。G2/A-02は未完了。

### 6.6 マウス選択と範囲外ドラッグ（専用試作）

既知の選択/スクロール再帰を受け、原文の選択所有者はDocumentDisplaySessionに維持し、試作のマウス入力をPresentation相当の接続部で扱う。理由は表示窓が変わる間にライブラリの局所選択モードを併用すると原文Anchorと自動スクロールの所有が二重になるため。利点は原文範囲と移動の一貫性、欠点はヒットテスト/キャプチャ/範囲外移動を接続側で管理し、単語/行単位の多重クリック等も別途実装する必要があること。新レイヤ/公開API/依存方向は変更しない。

左クリックのTextView内座標をスクロールOffset込みで局所位置へ変換し、最新Sliceの同一性を検証して原文位置へ渡す。Shiftは既存Anchorを維持する。単一ポインターだけを追跡し、他ポインターの移動/解放を採用しない。ライブラリへ局所ドラッグの開始を渡さず、原文選択の交差部分だけを描画する。ドラッグ中は窓内の余白による先行切替を行わず、原文Caretが窓外へ出たときに窓を切り替える。

表示外へのドラッグはUIタイマー1件、40msごとに縦1論理行または横32スカラー/改行境界ずつ延長する。縦を優先し、範囲端/再入/停止で不要な処理を重ねない。ScrollOffsetChangedから選択を更新せず、可視化は既存の最新1件のLoaded通知へ集約する。解放/キャプチャ喪失/文書切替/終了/キー操作でタイマーとポインター追跡を停止し、原文選択自体を消さない。本文やSliceを追跡状態へ保持しない。左押下で追跡を始め、移動時は同じPointerIdとキャプチャを確認する。移動イベントのボタンフラグだけでは終了と判定しない。

原文の境界補正では、左右の文字が現在の不変Slice内にあれば、その文字列を再利用する。端と範囲外では従来の原文読取を使い、余分なキャッシュや全文複製を加えない。離れた原文位置を交互に参照する際の割当を避けるためで、Sliceの寿命/所有者/補正規則は維持する。

影響は専用試作の入力/描画接続と内部の小さなドラッグ状態、Documentsの境界読取、対応単体試験に限定する。移行は状態/境界試験→専用GUIのヒットテスト/選択/範囲入替/解放/コピー→性能/OS差/通常採用の順とする。従来の通常UIは維持し、試作フラグを外せば戻せる。[検証記録](../validation-results/2026-10-31-source-pointer/README.md)：通常569件と10万ドラッグ反復が合格。小さい入力のmacOSで通常/逆方向/Shiftクリック/長行末尾の選択とコピー4件の読戻し一致を確認した。範囲外タイマーの実発火、長押し中の窓入替、予期しないキャプチャ喪失/タブ切替/再読込は未検証で、既知の再帰障害全体を解決済みとしない。全面スクロール、単語/行選択、多重クリック、タッチ/ペン、IME/結合列/双方向表示は別の未完了項目である。

### 6.7 有界表示の原文行番号（専用試作）

表示窓が原文の途中から始まると標準のLineNumberMarginは1から描画するため、専用試作では既存の左余白をSourceLineNumberMarginへ置き換える。理由は本文/ステータスが原文位置を示す一方で行番号だけが局所位置となる不一致を解消すること。利点は長行途中や複数行の窓でも原文の行を識別できること、欠点は独自のラベル描画とそのフォント/幅/寿命を検証する必要があること。層/公開API/依存方向は維持し、変更は試作内の表示接続とUI非依存の小さな数値対応に限定する。

SourceLineNumbersは原文先頭行・原文全行数・表示文書行数だけを保持する。表示行nは先頭原文行＋n−1とする。範囲を生成時と取得時に検証し、末尾を越えるラベルや64bit計算のオーバーフローを防ぐ。改行境界を分断しない既存Sliceの契約を使い、長行途中は同じ原文行、改行直後と末尾空行は次の原文行へ対応する。Contractsや検索結果へ局所行番号を追加しない。

表示窓を作る全経路で、表示文書と数値対応を一緒に余白へ渡す。描画はその表示文書と現在TextView.Documentが同じときだけ行い、文書交換途中に旧ラベルを新しい本文へ描かない。余白が追加で保持する文書は現在の短い表示文書1件だけで、原文/Lease/タブを保持しない。文書クリアで対応と参照を解除する。桁幅は原文全行数から計算し、同一本文の窓切替で桁数が増減しないようにする。描画量は可視VisualLine数に限定し、原文の全行走査や行番号一覧を作らない。

移行は数値/改行境界試験→専用GUIの行番号・ステータス照合と窓切替/空文書/文書切替→描画性能/OS差と他の残る受入→通常採用時にPresentationへ移す順とする。試作フラグを外せば従来候補へ戻せる。[検証記録](../validation-results/2026-10-31-source-line-numbers/README.md)：通常590件、Mac実機の1000行目の長行・末尾空行・空文書・タブ復元/全閉鎖を確認。50 MiBの前回版/今回版を長行/通常各1回比較し、接続/メモリ予算内だがtick16.7ms目標は未達。行番号余白での原文行選択、全面スクロール/可視行数、長押し自動移動、Unicodeの結合列/双方向表示と通常UI採用は別の未完了項目である。

#### 原文行番号余白からの行選択（2026-11-06）

専用試作では余白の押下も既存の単一ポインター所有者へ渡し、通常の局所文書選択を開始しない。押下/移動位置は現在のSliceで原文行へ変換し、DocumentDisplaySession.SelectLinesで原文の行開始から行末改行を含む範囲を選択する。逆方向はAnchorを元行の終了、Caretを対象行の開始へ置く。Shiftは既存Anchorの行を保持し、逆方向選択のAnchorが次行先頭なら直前の選択行へ対応させる。末尾空行は空選択とする。

目的は長行途中の局所行だけをコピーしてしまう問題の防止である。既存Documentsの行情報と試作のポインター状態だけを使い、全文走査/複製・追加Leaseを作らない。行境界はCRLF/スカラーを分断しないため、一般の位置補正に伴う遠隔本文読取を省く。ドラッグ中は元の原文行Anchorと最後にヒットした行を保持し、縦範囲外移動はその行を基準にする。改行後のCaretを基準に次の行を飛ばさず、横範囲外だけの移動では行選択を増やさない。取消/解放で行モードも解除する。

利点は原文範囲と既存コピー経路を維持できること、欠点は表示窓交換・マウスの可視化/捕捉を引き続き検証する必要があること。層・外部公開API・依存方向は変更しない。単体/反復性能→専用GUI→残る受入→通常採用時のPresentation移行の順を維持し、試作フラグを外せば戻せる。[結果](../validation-results/2026-11-06-source-line-selection/README.md)：通常602件、10万行選択反復、Macの通常/長行/逆方向/Shift/空行選択を確認。全面スクロール/可視行数・大容量/別OS等は未完了。

### 6.8 通常行の可視行数に合わせた連続窓（専用試作）

固定文字数の窓では、1行77単位の通常コードで15行程度しか保持できず、画面下が空白になる。既存のDocumentDisplaySlice（原文の連続範囲）を維持した比較として、CreateViewportSlice(target, maxLineChars, visibleLines)を追加する。行索引で周辺の要求行数を求め、末尾では前の行を補い、行頭〜行末改行を含む連続範囲を返す。要求は1〜512行、全体16 Ki単位まで。含まれる行が1行上限を越える、または全体上限を越える場合は従来の文字数窓へ戻す。境界は原文行から取得するのでCRLF/スカラーを分断しない。原文のAnchor/Caretは移動せず、最新Sliceだけが後続の局所イベントを受け付ける。

専用GUIはCODEVIEW_GUI_VIEWPORT=1で有効化する。TextViewの高さ/DefaultLineHeightから余裕2行を足した要求を作り、初回/対話/自動/選択の切出しへ共通に適用する。対話中のSizeChangedで要求が変われば窓を交換し、購読は文書切替/終了で解除する。原文の行番号・選択・コピーは既存の対応を使い、原文Leaseや全文複製を増やさない。

利点は既存の連続位置契約を変えず通常行の空白を減らせること。不利点は表示量増加に伴う描画/割当/CPUの増加と、長行が混在する場合や総量上限では行数を満たせないことである。新レイヤ/外部公開API/データ構造/依存方向の変更はない。通常製品へは採用せず、旗を外せば従来試作へ戻せる。単体/取得性能→専用GUIの通常/長行/リサイズ比較→全文スクロール/長行混在など残る評価→採否判断の順とする。

[検証記録](../validation-results/2026-11-06-viewport-lines/README.md)：通常622件、窓1,000回取得、Mac実機の通常行/拡大/復帰/次ページ、同DLLの50 MiB通常/長行と小入力の各方式比較を確認。小入力は15→36行になった一方でCPU/割当が増えた。接続/メモリ予算内、tick16.7msは未達。スクロールバーは局所範囲のままであり、これを全文スクロールや長行混在対応の完了にはしない。

長行混在と全文スクロールのための[行別投影への変更案](../bounded-projection-proposal.md)は2026-11-06に承認を受けた。既存の連続Sliceの位置契約と利用経路は維持し、6.9で行別投影コアを別に追加する。通常UIへの採用は未完了である。
