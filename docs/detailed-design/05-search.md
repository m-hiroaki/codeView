# 05 検索

[索引](README.md) / 関連：[共通規約](01-contracts.md)、[読取](03-files-tree.md)、[本文](04-documents-tabs.md) / 上位：基本設計6.1〜6.3、アーキテクチャ設計5.2・6.3

## 1. 型と呼出契約

| 型・配置 | データ・操作 |
| --- | --- |
| `SearchOptions` / Search | `MatchCase`、`WholeWord`、`UseRegex`。通常の既定値はすべてfalse |
| `WorkspaceSearchRequest` / Search | 固定ルート・除外・文字コード指定、語、Options、RequestId、WorkspaceEpoch・SearchEpoch |
| `InFileSearchRequest` / Search | TabId・DocumentVersion・InFileEpoch、語、Options、探索方向・開始位置 |
| `SearchHit` / Search | FileScanId、パス、TextRange、一致長、短い抜粋と抜粋内の一致範囲、SourceStamp |
| `SearchEvent<T>` / Search | `Hits(batch<T>)`、`FileCommitted(id)`、`FileInvalidated(id, error)`。通常検索のTはSearchHit、定義探索はDefinitionCandidate |
| `SearchProgress` / Search | 走査済み・対象外・失敗の件数、評価バイト数。最新1件だけ保持する |
| `TextSearch` / Search | `StartWorkspace(request, ct)`はSessionを返す。本文内の`ScanReadViewAsync(request, lease, consume, ct)`は後続実装 |
| `WorkspaceSearchSession` / Search | 有界イベント受信口、Completion Task、最新Progress、Terminal。取消トークンは操作所有者が管理 |
| `LiteralMatcher` / Search | チャンク状態を持つ通常・単語単位照合 |
| `RegexLineMatcher` / Search | 上限内の1行に対する正規表現照合 |

列挙・読取・照合は検索枠のワーカー1件で進める。ReadViewは本文側の契約を利用し、AvaloniaEdit型を持たない。照合関数は行・オフセット・境界の規則を共有し、横断とファイル内で結果の意味を変えない。

本文側の逐次入口はDocumentReadLeaseのVisitChunksを利用する。チャンクは上限16 Ki単位で実際には短い場合もあり、照合側は長さ固定を仮定しない。短いチャンクを検索側で集約する場合も、毎回過去の全文や長い語の接頭辞をコピーせず、有界バッファへ追記して処理する。本文側での一律集約は初期の走査比較で時間が増えたため採用せず、必要性は照合・初期応答を含めてD-04で評価する。

バッチのTだけを型引数とし、検索処理全体を汎用フレームワークにしない。NavigationがSearchの返却用契約を利用し、SearchがDefinitionCandidateの具体型やNavigationへ依存しない。終了情報では生成・返却件数と、無効化を除いた確定件数を区別し、画面件数は採用済みレコードから求める。

## 2. 条件の検証

空語は実行しない。入力の前後空白は自動削除せず、空白だけの語も通常の検索語として扱う。行をまたぐ検索は対象外とし、通常語に改行がある場合は実行前に案内する。正規表現は各行の改行文字を除いた内容に適用し、複数行を結合しない。

入力長は初期実装で16 Ki UTF-16単位までに固定し、超過は黙って切らず条件エラーを返す。通常語の不正なサロゲート列も条件エラーにし、補助平面文字の片側だけを検索しない。正規表現の式と結果のスカラー境界は4章の規則に従う。検証・Regex構築もUI上で実行せず、入力世代に対応する結果だけを採用する。上限を固定しただけでD-10のRegex/表示検証を完了としない。

通常検索の比較は`Ordinal` / `OrdinalIgnoreCase`を採用する。NFC等の正規化、幅・濁点の同一視はしない。正規化なしのコードポイント一致を意図し、大小無視だけは明示した.NETのOrdinalIgnoreCaseの意味に従う。独自の単純な大文字変換で代用しない。正規表現はCultureInvariantとMatchCaseに応じたIgnoreCaseを候補にし、Inlineオプションは.NETの式の意味に従う。RegexのCompiled化や無制限のパターンキャッシュは初期採用しない。

## 3. 通常・単語単位照合

1. Decoderから受けた文字チャンクへ、前回末尾の検索語長-1文字と単語判定に必要な前後のUnicodeスカラー値をつなげて評価する。
2. 一致候補がチャンク末尾にかかり、右側の単語境界が確定しない場合は次のチャンクまたはEOFまで保留する。
3. 結果の絶対オフセットを計算し、既に確定した範囲の一致を再送しない。
4. 通常は非重複一致とし、`aaa`から`aa`は先頭1件。次開始位置は一致末尾とする。
5. 改行を含む一致を作らず、CRLF・CR・LFの確定時に行・列を更新する。

単語要素はUnicodeのLetter、LetterNumber、DecimalDigitNumber、ConnectorPunctuation、NonSpacingMark、SpacingCombiningMark、Formatを含む。前後が単語要素でないか本文端の場合に単語境界とする。Rune単位の分類を使い、ASCIIだけの境界判定や.NETの`\b`を無条件に代用しない。C#の`@`は単語要素に含めず、参照探索で取得した語の`@`を除去する。

結果は一致開始の行・UTF-16列で示す。チャンクの持越しは検索語長と少量の文脈に限定し、行全体や過去の全チャンクを保持しない。語長の上限とバッファ使用量の関係は性能試験で確認する。

### 3.1 逐次照合の実装境界

Search内のLiteralMatcherはCreate(query, options)、Push(span, consume, ct)、Complete、Abort、Resetを持つ。File/Document/UI型を持たず、返すのは原文のTextRangeだけ。通常語の空・改行・上限超過・不正サロゲート、誤ってUseRegexを指定した生成要求はInvalidPatternにする。文字列の空白を削除しない。

バッファは検索語長+16 Ki+4 UTF-16単位、最大32,772単位に固定する。任意の大きさの入力も16 Ki以下ずつ追記し、検索開始位置より前の全文を再評価しない。空きがなくなった時だけ既評価部分を圧縮し、左スカラー用の最大2単位と未評価の語長分/右文脈を残す。毎チャンクで語の接頭辞全体をコピーしない。ReadOnlySpan.IndexOfのOrdinal/OrdinalIgnoreCaseで照合し、Unicodeの大小文字規則を独自に実装しない。

単語検索では右側スカラー用の2単位を次チャンク/EOFまで保留する。左と右はRuneで分類し、曖昧なチャンク末尾を単語端と誤認しない。一致を採用した時だけ語長分進め、単語境界で拒否した候補は1単位進めて次を探す。TextCursorは探索開始位置まで原文を一度ずつ進み、圧縮後もOffset/行/列とCRLF状態を維持する。

consumeがfalseなら即座に走査終了、取消はOperationCanceledException、利用側の例外はそのまま伝える。終了/失敗/Abortでは保持文字を消去する。Abortは読取失敗をEOFとして扱わず、保留中の末尾一致を返さない。Resetは終了後だけ許可し、同じ語/バッファで次ファイルのオフセット/行/列を0/1/1へ戻す。ファイルごとに最大64 KiB程度の文字配列を作り直さない。コールバックのデリゲートもチャンクごとに生成せずセッション内で再利用する。

仕様上の理由は通常/本文内検索の結果を統一し、任意の長行でも全文保持・不完全な単語判定を避けること。利点は正確性と保持量をUI/本文候補なしで検証できること、不利点は右文脈/EOF/読取失敗とバッファ再利用の状態管理が必要になること。既存のSearch内の設計済み照合責務を実装し、層・依存方向を変えない。照合単体→ReadLease/FileReader接続→仮結果/取消/有界イベント→UIの順に進め、現段階で全文検索や本文内検索の完成とはしない。

参照：[比較方法の指針](https://learn.microsoft.com/en-us/dotnet/standard/base-types/best-practices-strings)、[SpanのIndexOf](https://learn.microsoft.com/en-us/dotnet/api/system.memoryextensions.indexof?view=net-10.0)、[Rune分類](https://learn.microsoft.com/en-us/dotnet/api/system.text.rune.getunicodecategory?view=net-10.0)。

## 4. 正規表現照合

1. セッション開始時に有限のRegexTimeoutでRegexを1つ構築し、不正式はInvalidPatternとして走査を始めない。
2. 改行を除いた1行をRegexLineCharsまで組み立てる。超過後は内容の追加を止め、次の改行まで読み流して未評価行数を加算する。短い接頭辞だけを検索したことにしない。
3. 1行内を順に評価し、WholeWordが有効なら通常検索と同じ外側の単語境界も確認する。
4. 0文字一致の後は次のUnicodeスカラー値境界へ進め、行末の0文字一致はその行で一度だけ返して終了する。
5. タイムアウトは当該検索全体を停止する。時間制限は取消Tokenの代わりではないので、評価間・行間にも取消確認を行う。

.NETの式はUTF-16上の結果を返すため、補助平面文字の途中を指す結果は選択しない。サロゲート境界に合わない一致を未評価扱いで数えて除外する方針に固定し、勝手に一致範囲を拡張して式の意味を変えない。`.`、文字クラス、0文字一致、明示的な補助平面文字は単体試験し、D-10の制約表示/検索セッションでの伝達は後続で確認する。

任意の正規表現を別の断片へ分割するとlookbehind等の意味を維持できないため、長行を固定重なりで分割して完全検索と称さない。[Microsoftの正規表現の指針](https://learn.microsoft.com/en-us/dotnet/standard/base-types/best-practices-regex)と[タイムアウト付きコンストラクター](https://learn.microsoft.com/en-us/dotnet/api/system.text.regularexpressions.regex.-ctor)を参照する。タイムアウトは悪意ある任意パターンに対する完全な保護境界とは扱わない。

### 4.1 行照合の実装境界

RegexLineMatcherはCreate/Push/Complete/Abort/Resetを持ち、1セッション1個のRegexと最大1,048,576 UTF-16単位の文字配列を再利用する。CreateはQueryChars以内の非空パターンとUseRegexを確認し、CultureInvariantとMatchCaseに応じたIgnoreCaseで有限100msのRegexを構築する。Compiled・全体キャッシュ・NonBacktrackingへの一律変換はしない。式内のオプションは.NETの規則に従う。テスト用の行/時間上限は既定値以下だけを許可し、利用設定へ増やさない。

PushはCR/LFまで蓄積し、CRLFは1改行として扱う。Completeは最後の空行も1回だけ評価する。行が上限を超えた時点で保持内容を消去し、次の改行/EOFまで読み流してSkippedLongLinesへ1件加算する。先頭1 Mi単位だけを検索しない。位置はTextCursorと行開始オフセット/行番号から作り、通常検索と同じ原文UTF-16単位で返す。

評価はRegexのインスタンスEnumerateMatches(span)を使い、行のstring化やMatchオブジェクト一覧を生成しない。元の行全体を入力にし、lookbehind、アンカー、分岐優先順位と非重複結果を維持する。WholeWordは得られた一致の外側を共通Rune分類で検査する後段フィルターで、式への境界断言の付加や、拒否した一致内の別分岐/重なりの再探索はしない。例えば`foo|foobar`で`foobar`を検索しWholeWordが有効な場合、先に得た`foo`が境界不一致なら`foobar`へ置き換えて再評価しない。

0文字一致の後は次のスカラー境界より前の0文字候補を採用せず、行末の0文字一致は1回で終える。基礎エンジンはUTF-16で列挙するため、非0長でサロゲートを分割する候補や、式自身が指した不正な0長境界はSkippedScalarMatchesに数える。正しい0長進行の途中で通るサロゲート内部の0長候補は数えない。この件数は除外した候補数で、未評価の文字数ではない。範囲を補正して別の一致を捏造せず、元のRegex列挙と`\G`等の意味を保つ。

エンジンのMoveNextがタイムアウトした場合はError=RegexTimedOut・IsFinished=trueでfalseを返す。同じ検索が次ファイルへ続かないよう、タイムアウト後はResetを拒否する。取消と利用側の例外はAbortしてそのまま伝え、利用側が投げたRegexMatchTimeoutExceptionまでエンジン失敗へ変換しない。Abortは未確定行をEOFとして検索せずに消去する。正常終了/Abort後のResetは行/CR/位置と各ファイルの統計を初期化し、Regex/配列は再利用する。所有は直列ワーカー1件とし、通知中に照合器を再入操作しない。

理由は長行の保持/割当とRegexの意味の両方を守るため。利点は上限/位置/取消を通常検索と共有し、ファイル数/行数に比例する文字列生成を避けられること。不利点は長行と非スカラー候補が未評価になるため、検索終端と画面へ件数/制約を伝える接続が必要なこと。影響はSearch内部と検索仕様の記録で、層・依存方向・本文モデルを変えない。単体境界試験→ReadLeaseコア測定→ファイル/検索イベント→UIでの制約表示の順に進める。

参照：[Span上の列挙](https://learn.microsoft.com/en-us/dotnet/api/system.text.regularexpressions.regex.enumeratematches?view=net-10.0)、[.NET 10の列挙器](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Text.RegularExpressions/src/System/Text/RegularExpressions/Regex.EnumerateMatches.cs)。

## 5. 全文検索の処理手順

```text
条件検証・固定
for 対象パス in DirectoryReaderの逐次列挙:
    取消確認
    FileScanIdを採番し、文字コード準備
    仕様上の対象外なら分類して次へ
    読取・照合してHitsを有界キューへ送る
    成功・更新なしならFileCommitted
    途中失敗・変更ならFileInvalidated
    ファイル資源を解放し進捗の最新値を更新
finally:
    取消・上限・失敗を含む終了情報を確定
    writerを完了しTaskの完了を観測可能にする
```

結果はファイルの評価が終わるまで「検証中」として表示し、移動を無効にする。FileCommittedを採用した時点で移動可能にする。全結果をファイル完了までワーカーの巨大な配列へ溜めない。

読取途中の失敗・変更はFileInvalidatedで当該FileScanIdの結果だけを除去し、失敗件数を更新する。検索ワーカーは1つなので、未確定ファイルは同時に1件まで。ハンドルや本文は結果に残さない。

ResultLimitは生成・返却した結果の総数に適用する。途中無効化によって表示件数が減っても予算を戻して無制限に生成し続けない。上限に達した場合は即座にLimitReachedとして止め、現在ファイルの仮結果も部分結果であることを表示する。仮結果はジャンプ不可のままとし、ファイル未完了である旨を明記する。ちょうど上限で本当は全件だった場合も、残りの走査をしていないなら未完了とする。

結果一覧は走査順に追加し、リポジトリ全体でのソートを待たない。順序はOS列挙に依存し得る。同一行の複数一致も別結果とする。抜粋は最大SnippetCharsに収め、長い行も一致周辺だけを保持する。一致後の文脈が必要なら固定長だけ遅延して生成し、一致全体や行全体をコピーしない。

### 5.1 抜粋取得の実装境界

LiteralMatcherとRegexLineMatcherは同期の一致コールバック内だけ`CaptureSnippet()`を許す。理由は、Regexでは行末時点で前方の一致を通知するため、外部の小さな末尾バッファから原文を復元できないこと。既存の照合バッファを参照し、SearchSnippet（Text、MatchStart、MatchLength）へ最大200 UTF-16単位だけコピーする。大小文字を含め原文を保持し、前方文脈は最大60単位、CR/LFを越えず、両端でサロゲートペアを切断しない。長い一致は先頭200単位以内を表示し、抜粋内の一致長だけを短縮する。元のTextRangeは変更しない。

通常照合は通知時点で保持している範囲だけを抜粋に使い、後続文脈のために読取を待たない。従ってチャンク境界により文脈量が変わり得る。利点は本文/行の再読取・全体コピーと別の文脈バッファが不要なこと、欠点は一定長の前後文脈を保証しないこと。CaptureSnippetを使わない照合では文字列を生成しない。通知の正常終了・false・例外のいずれでも取得権を失い、コールバック外の呼出しは拒否する。照合器は単一ワーカーが直列に所有し、コールバックからPush/Complete/Reset/Abortを再入させない。

影響範囲はSearch内部の照合器と結果生成に限定し、層/依存方向は変更しない。既存のTextRangeコールバックを維持し、まず抜粋の単体試験と照合性能回帰を行い、次にワーカーがコールバック内で取得した抜粋をSearchHitへ格納する。ワーカー/イベント/UIへの接続前はP4-04/P4-05の完了とはしない。

### 5.2 逐次ワーカーの実装境界

StartWorkspaceは固定要求からTask.Runを1件だけ開始する。DirectoryReader.WalkFilesの深さ優先列挙とFileReader.Prepare/ReadChunksを同じワーカーで直列実行し、全パスの配列・索引・本文モデルを作らない。照合器とコールバックはセッションで再利用する。検証後の読取失敗/変更ではAbortで保留照合を破棄し、既存の仮結果をFlushした後にFileInvalidatedを送る。成功時だけCompleteでEOFを照合してFileCommittedを送る。

Binary/NotRegularFileと列挙上のリンク/除外/特殊エントリは対象外へ加算する。デコード失敗・読取不可・変更等は失敗件数とErrorCode別件数へ加算し、代表例だけ20件以内で保持する。サブディレクトリの失敗は継続、ルート列挙失敗は検索全体をFailedとする。除外ディレクトリの配下件数は数えるために列挙しない。Regexタイムアウトは検索を停止し、そのファイルを確定しない。評価済み行/長行未評価/非スカラー一致除外はファイル間で集計する。Completedでも失敗/未評価を含む場合はIsPartialを立て、完全結果と区別する。

SearchProgressのReadSourceBytesは再読取が成功したファイルのSourceStamp.LengthBytes合計、DecodedCharactersは照合入口へ届いた文字数とする。前者は論理入力量で、検証パスの追加I/O・途中失敗分・物理読取量や、Regexで実際に照合したバイト数を表さない。更新は最新1値・100ms間隔と終了時の強制更新に限定する。

## 6. キュー・進捗・完了通知

結果用の有界Channel相当を1セッションに1つ持ち、HitsはBatchSizeまで、キューはResultQueueBatchesまでとする。FileCommitted / Invalidatedも同じ順序付き経路に送る。進捗は別の最新1値を上書きし、ProgressInterval以上の頻度で通知を増やさない。

UIは4msまたは256件の予算まで取り出し、次の短い処理へ譲る。ドレイン通知は同時に1件だけ予約し、追加要求を集約する。処理後、キューの再確認と予約解除の競合で通知を落とさないよう、解除後の再チェックを行う。

正常・通常失敗の完了表示は、writer終了かつ受信キューを排出した後に確定する。ワーカーTaskの終了だけで先に「完了」と表示しない。取消時は残キューを破棄し、採用済みの確定結果を残す。未確定ファイルの結果は破棄する。新検索では旧ドレインと完了通知を世代で不採用にする。

例外・取消でFileInvalidatedが送れない場合、終了情報の未確定FileScanIdでUIが同じ無効化を行う。取消時はこれに加え、UIがFileCommittedをまだ採用していない全仮結果を破棄する。ワーカー側が既に確定通知を送信して未確定ID=nullでも、その通知がキュー破棄で失われる場合があるためである。終端情報は満杯キューへの投入を無期限に待つ経路にせず、Taskの終端結果として保持する。writer完了・終端結果・未確定IDと表示側の確定状態を必ず観測する。

### 6.1 セッションと終端の実装境界

Sessionは単一writer/readerのBoundedChannel（Wait、8イベント、同期継続なし）とCompletion Taskを所有する。Hitsは最大128件の読取専用バッチとし、送信後に同じListを変更しない。先頭一致はすぐFlushし、その後は128件・100ms経過・ファイル末尾・結果上限でFlushする。イベント投入はワーカースレッドで取消可能なWriteAsyncを待ち、UIでは同期待機しない。

生成1万件で照合を止め、上限到達を通常の読取エラーへ変換しない。GeneratedHitsには生成済み件数、ReturnedHitsにはチャネルへ投入済みの件数、CommittedHitsには投入済みFileCommittedに対応する件数を記録する。取消時は投入待ち/手元バッチが破棄されるため生成と返却が異なり得る。画面へ採用済みの件数はこの値から推定しない。

通常の失敗/取消/上限ではSearchCompletionをTask結果として返し、チャネルを完了する。未知の例外や当該要求の取消と対応しないOperationCanceledExceptionは、終端情報を伴うSearchWorkerExceptionでTaskとチャネルを失敗させる。取消の扱いは要求トークンが取消済み、かつ例外のCancellationTokenが要求トークンと等しい場合に限定し、同時に発生した別トークンの取消を隠さない。Terminalはwriter完了前に公開する。操作所有者は両経路の失敗と終端情報を観測して、必要なら致命的経路へ進む。初めから取消済みでもワーカーの後始末を実行し、writerを未完了で残さない。

従来案のwriter引数からSession返却へ具体化した理由は、終端先着と満杯時の取消を受信口/Task/最新進捗の1つの寿命で観測するため。利点は無制限の別通知キューが不要なこと、欠点は操作所有者がキュー排出とTask完了を別々に確認する必要があること。影響はSearch内部の要求・結果契約とOperations接続に限定し、層/依存方向は維持する。単体・ワーカー性能→Operationsの世代/処理枠→UIドレインの順で接続する。Operations側の実行1件/最新待機1件と、世代を確認するTryRead/TryFinalizeは[詳細設計02の1.1](02-runtime-ui.md)へ、UIの通知集約/取消/仮結果処理は同6.1、結果移動は[04の6.1](04-documents-tabs.md)へ接続済み。定義/参照探索の共用枠への接続、包括的な実機受入は未完了であり、P4-05全体の完了とはしない。

## 7. ファイル内検索

### 7.1 基準方式

タブごとに条件、InFileEpoch、DocumentVersion、走査済み区間、保持一致位置、件数状態を持つ。条件変更ではInputDelayの後、旧処理を取消し先頭からの段階的走査を開始する。本文ReadLeaseを使い、FileReaderでディスクを再読込しない。

各チャンクまたは短い時間区切りで位置を返し、全件完了を待ってハイライトしない。ハイライトは現在の可視行に関係する位置だけを描く。保持上限へ達した後は「少なくともN件」とし、残りを総件数確認のためだけに無制限に走査し続けない。

### 7.2 次／前移動と追加走査

- 次は現在の一致末尾以降から、前は現在の一致開始より前から、方向に近い一致を探す。現在の0文字一致を繰り返さないよう次のスカラー境界へ進める。
- 保持位置に該当があれば即座に移動する。なければ背景の全体走査を中断して方向別要求を優先し、同じ検索枠内で必要区間だけ評価する。
- 前方向の通常検索は範囲ごとに走査して最後の一致を求める。正規表現は行単位の元の左から右の意味を維持し、方向指定だけのためにRegexの解釈を変えない。
- 端まで未検出なら一度だけ折返し、既に評価した開始地点へ戻ったら終了する。「検索中」「見つかりません」「折返し」を表示で区別する。
- タブ切替は実行中の本文内検索を取消し、条件・保持位置をそのタブに残す。再度選んだ時に同じ文書版なら再利用し、未走査範囲は再開または再走査する。

### 7.3 比較評価

可視領域を先に走査してから残りを埋める方式と、次／前を必要時だけ評価する方式をPhase 4で比較する。区間表は統合・上限管理し、スクロールごとに区間数を増やし続けない。長い1行の正規表現を可視部分だけに切って完全一致としない。採用が決まるまでは7.1を評価基準とし、D-04で結果を記録する。

### 7.4 ファイル内検索の実装

通常の本文表示にCtrl/Cmd+Fと検索メニューを接続した。検索欄の確定済みTextを受けて150ms後に走査する。Avaloniaの変換途中文字列はTextPresenterに保持される。[Avalonia 12.1.3の入力クライアント](https://github.com/AvaloniaUI/Avalonia/blob/12.1.3/src/Avalonia.Controls/TextBoxTextInputMethodClient.cs#L135-L145)

アクティブタブの本文ReadLeaseを専用の1枠で走査し、既存の通常照合器と正規表現照合器を使う。結果を有界のバッチで反映し、可視行の背景に描画する。保持上限は1タブ10,000件で、到達時は最低件数を表示する。正規表現で長さ上限を超えた行と、補助平面文字の途中を指すため除外した一致は、検索欄の下に件数を表示する。次・前の移動後も、その探索で判明した未評価の理由を表示する。

保持済み範囲で次・前が決まる場合はそこへ移動する。追加走査は元の先頭から照合して、非重複、単語境界、行アンカーの意味を保ち、方向の候補が決まった時点で終了する。前方の探索や折返しには末尾までの走査が必要になる場合がある。窓からの再開方式との比較と大容量での評価はP4-07に残す。

タブ切替、入力変更、再読込、閉鎖で旧処理を取り消す。再選択したタブでは条件と同一本文の保持結果を再利用する。再読込は条件を引き継いで一致を再構築する。移動時も入力世代と表示中の本文を確認する。通常表示向けの実装で、表示投影試作は対象外。
