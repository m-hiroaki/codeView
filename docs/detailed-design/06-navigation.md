## 1. 探索契約

`ISymbolNavigator`は簡易探索の内部契約とし、Navigationの`SimpleSymbolNavigator`が実装する。意味解析による探索は8節に記載する。

| 操作・型 | 入出力 |
| --- | --- |
| `FindDefinitions(request, ct)` | 固定ルート・除外・文字コード、識別子、操作識別を受け、宣言候補と終了情報を配信する |
| `FindReferences(request, ct)` | 同じ情報を受け、大小区別の単語一致で参照箇所を配信する |
| `WorkspaceSearchRequest` | 比較用の名前、ワークスペース条件、RequestId・WorkspaceEpoch・SearchEpoch。識別子の抽出元となる本文は保持しない |
| `WorkspaceSearchSession` | 有界の `SearchEvent<SearchHit>`、進捗、終了情報。定義は候補の種別名を抜粋に含める |

`SimpleSymbolNavigator` は既存の検索イベントを共用し、候補の原文位置・抜粋を返す。ファイル確定・無効化・終了は05の規則に従う。Operationsは検索枠を得た時点で対応する入口を呼び、候補数と全件評価の状態を見て自動移動を判断する。本文を開く責務は移動処理が持つ。

## 2. 識別子の抽出

1. 選択がある場合、改行・空白・複数トークンを含まず1識別子であることを確認する。
2. 未選択ならカーソル位置のスカラー値を調べる。区切り直後では直前が識別子の末尾ならその語を採る。どちらにも属さなければ有効識別子なしとする。
3. Unicode文字・数字・結合文字等の構成規則は通常検索と共有し、先頭の数字を許可しない。C#の`@name`は元の選択範囲に`@`を含め、比較用からだけ除く。
4. C#予約語をそのまま指定した場合は識別子でないとして通知する。`@class`等は識別子として扱う。コンテキストキーワードは宣言位置で判断し、抽出だけで一律に拒否しない。
5. C#とC/C++は各言語の規則で定義を探索する。他の言語では対応範囲を通知する。参照は有効な単語なら同じ名前照合を利用できる。

Unicode正規化や名前空間・ジェネリック引数の付加はしない。`obj.Method`全体の選択は拒否し、Method単体の選択を案内する。Unicodeエスケープで記述した識別子は初期版の保証対象外とし、通常表記と黙って同一視しない。

### 2.1 識別子抽出の実装（2026-11-07）

設計済みNavigation内の`IdentifierExtractor`で、供給された原文Spanから名前と元の範囲を得る。本文/UI型を参照せず、通常検索のRuneカテゴリを再利用する。先頭はUnicodeのLetter/LetterNumberまたは`_`、以降は通常検索の単語要素とする。最大4,096 UTF-16単位（`@`を除く）で、超過・不正範囲・サロゲート途中・空・複数語・エスケープ表記を拒否する。選択があればCaretより優先し、未選択では語の途中/直後/`@`上を扱う。C#予約語は`@`付きのみ許可し、文脈キーワードは抽出で拒否しない。正規化/大小文字変換は行わない。

NV-01の正常/異常/Unicode/上限を35単体ケースで確認。実装は既存設計の内部責務で、外部公開API・層・依存方向・本文データ構造を変更しない。明示要求時だけ有界走査し、起動/描画/常駐索引を追加しない。UI側の原文取得と参照検索の接続はP5-06で行う。定義解析・探索契約全体とG4/G5は未完了。

## 3. 簡易字句走査

C#の走査は除外後の通常の`.cs`ファイルを対象とし、厳格にデコードした文字チャンクから逐次トークンを得る。改行は位置に反映し、宣言の途中の改行は区切りにしない。全文AST・参照解決・プロジェクト索引を作らない。

| 状態 | 処理 |
| --- | --- |
| `Code` | 識別子・キーワード・記号・数値を読む。コメント・リテラル開始を判定 |
| `LineComment` | 改行まで候補判定から除外 |
| `BlockComment` | 終端まで除外し、終端未完なら解析未完了 |
| `String / Char` | バックスラッシュエスケープを含め終端まで除外 |
| `VerbatimString` | 二重引用符によるエスケープを扱って除外 |
| `RawString / InterpolatedString` | 終端規則を確認できる対応パターンだけ除外。安全に終端を認識できない場合は解析非対応として当該ファイルを未評価にする |

リテラル中の`class Foo`等をコードとして検出しない。補間文字列やraw文字列は単純に次の引用符まで読み飛ばす実装にしない。対応パターンと未対応の組合せはPhase 5の固定データで示す。不完全構文・非対応構文で文脈を復元できない場合は、誤った候補を確定せず当該ファイルを無効化する。

`#if`等の条件は評価せず両分岐を読むため、同名候補・非コンパイル対象の候補が含まれ得る。プリプロセッサー行を候補としては扱わない。字句処理の位置は元本文に対応し、コメント削除後の文字列上のオフセットを返さない。

保持は現在トークン、宣言用の有界な直前トークン列、括弧・型本体の文脈スタック、対象名と少量の抜粋に限定する。解析上限は[共通予算](01-contracts.md)のLexerTokenChars・DeclarationTokens・DeclarationChars・LexerDepthを参照する。超過は未評価として通知し、巨大な宣言を黙って欠落させない。Phase 5前に解析予算として固定する。

### 3.1 逐次字句走査の実装（2026-11-07）

Navigationの`CSharpLexer`は任意分割のUTF-16を受け、識別子/キーワードの原文、概略数値、単一記号、本文を保持しないリテラルトークンを返す。位置は共通TextCursorによる64bit原文Offsetと1始まり行/UTF-16列。CRLFとサロゲートをチャンク途中で切っても位置を保つ。C#のNEL/LS/PSは字句上の改行として扱い、位置表示は既存本文のCR/LF契約に従う。条件付きコンパイルの式は評価せず、指令行以外の両分岐を走査する。

通常文字列/文字、逐語文字列、単行/複数行raw、通常/逐語/raw補間を処理する。補間の入れ子・式内の括弧/コメント/リテラルを追跡し、内容は宣言トークンへ出さない。rawは引用符数、複数行終端位置、`$`に応じた波括弧数を確認する。単純な書式部は除外し、書式部に引用符・開き波括弧・改行がある未対応形、Unicodeエスケープ識別子、未完了リテラル、不正UTF-16、上限超過は明示的なエラーとする。C#コンパイラー相当の数値/構文検証やrawインデント値の生成は行わない。

先読み16 Ki + 4単位、語/数値4,096単位（`@`のみ1単位追加）、raw開始区切りの引用符/`$`各4,096、リテラルと補間内括弧の合計深さ1,024を上限とする。長いコメント/リテラル本体を保持しない。`Push`中のトークンは仮で、`Complete`成功時だけファイルを確定できる。取消/消費側停止/例外時は作業領域をクリアし、終了後だけ再利用できる。

`CSharpFileLexer`は既存FileReaderから厳格復号済みチャンクを借り、`.cs`に限定する。Stamp確認後にEOFを確定し、読取/解析の失敗・停止時は`CanCommit=false`を返して当該ファイルの候補を無効化できる。借用したPreparedTextの所有は呼出元のまま。宣言側の予算と確定判定は4.1節、候補配信と画面接続は5.1節に記載する。定義探索を要求したときだけC#走査を行う。

[76件の単体・実ファイル検証と補助スモーク](../validation-results/2026-11-07-csharp-lexer/README.md)。境界の仕様参照：[C#字句構造](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/lexical-structure)、[raw文字列](https://github.com/dotnet/csharplang/blob/main/proposals/csharp-11.0/raw-string-literal.md)、[補間文字列](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/tokens/interpolated)。

## 4. 宣言候補の検出

| 種別 | 初期対応の形 | 判定に使う文脈 |
| --- | --- | --- |
| 型 | `class N`、`struct N`、`interface N`、`enum N`、`record N`、`record class/struct N` | 名前トークンの完全一致。空の型本体を表すセミコロンと、型の入れ子も扱う |
| Delegate | `delegate ReturnType N(...)` | 戻り値の後の名前・引数列・終端 |
| Method | `ReturnType N(...) { ... }`、`=> ...;`、インターフェース等の`;`宣言 | 型本体直下。修飾子・属性・ジェネリック引数・制約を有界窓で読む |
| Property | `Type N { get; ... }`、`Type N => ...;` | 型本体直下で引数列のないメンバー形 |
| Field | `Type N;`、`Type N = ...;`、`Type A, N;`、`fixed byte N[16];` | 型本体直下。初期化式の括弧・波括弧と固定長バッファーの長さ式を読み飛ばす |

メソッド・プロパティ・フィールドは、メソッド本体等の内部にいる場合は候補にしない。呼出し`obj.N()`やローカル変数は宣言扱いにしない。対象名の一部だけの一致は除外する。

コンストラクター、演算子、インデクサー、明示的インターフェース実装、ローカル関数などは既知の精度制限として記録する。単純なメソッド・型の受け入れ要件は固定データで必ず確認する。

メンバーの型に現れる `delegate*<...>` は、呼び出し規約、入れ子の関数ポインター型、参照修飾子を含めて読み取る。呼び出し規約名や型の組み合わせの妥当性は検証範囲外。 [C#の関数ポインター](https://learn.microsoft.com/en-us/dotnet/csharp/misc/cs0059#function-pointer-calling-conventions-and-return-types)

条件付きコンパイルのディレクティブ行は読み飛ばす。プロジェクトごとのシンボルは評価しないため、`#if false` 内や非アクティブな分岐の宣言も候補になることがある。

候補の位置は名前の開始。重複は同ファイル・同オフセット・同種別に限りまとめ、同名の別宣言は残す。候補確定のために必要なトークンの終端を待ってから返す。解析未完了で仮候補を返していた場合はFileInvalidatedで取り消す。

### 4.1 宣言候補検出の実装

`CSharpDeclarationScanner`は厳格復号済みの字句を順に受け取り、対象名と大小文字まで一致する宣言の種別と原文範囲を返す。`@N`は比較時に`N`として扱い、返す範囲には`@`を含める。同名の型やオーバーロードは位置ごとに残す。

名前空間と型の直下を追跡し、メソッド本体などのブロックは括弧の対応を確認して読み飛ばす。フィールドは初期化式内の括弧や型引数を考慮して宣言子を分ける。属性、改行、ジェネリック、基本的な制約、式形式のメソッドとプロパティ、アクセサーと初期化子のあるプロパティを固定試験に含めた。

宣言ヘッダーと初期化式の作業範囲は終端を含めて256トークン・16 Ki UTF-16単位、スコープと括弧は合計1,024階層まで保持する。上限超過や括弧の不整合、未完了の宣言ではそのファイルを確定しない。候補は字句読取と宣言走査の両方が完了するまで仮扱いとする。式と制約の型解決、C#構文全体の妥当性検証は実装範囲外。

メンバーの型名には `async`、`partial`、`required`、`file` も使える。修飾子として読み進めてメンバーを認識できなかった場合は、その語を型名の先頭として読み直す。戻る範囲は既存の宣言ヘッダー内に限る。[C#の文脈キーワード](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/contextual-keywords)

メソッドとデリゲートのジェネリック制約では、`where`・型パラメーター名・コロンの並びで次の制約句を判定する。制約に使う型名や別名の `where` は、同じ制約句の一部として扱う。[C#のジェネリック型制約](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/where-generic-type-constraint)

通常画面への接続は5.1節に記載する。固定試験は正常系、呼出し・ローカル変数の除外、同名、原文範囲、上限、実ファイルの確定・無効化を含む47件。macOSの通常テストは.NET 938件とPython 112件が成功した。

### 4.2 C/C++の定義候補

CとC++は共通の探索範囲を使う。拡張子は大文字小文字を区別せず、`.c`、`.h`、`.i`、`.ii`、`.cc`、`.cp`、`.cpp`、`.cxx`、`.c++`、`.hh`、`.hpp`、`.hxx`、`.h++`、`.ipp`、`.inl`、`.tpp`、`.ixx`、`.cppm`を扱う。ヘッダーの定義と別ソースの定義は、各ファイルの元の位置を持つ候補になる。

| 種別 | 検出する代表形 |
| --- | --- |
| 関数 | 本体のある関数と型のメンバー。基本的なテンプレート、修飾された名前、コンストラクターの初期化リスト、`= default`、`= delete`を含む |
| 型と別名 | 本体のある`class`、`struct`、`union`、`enum`と、`typedef`、`using Name = …` |
| 変数・フィールド・列挙子 | 名前空間、ファイル、型の直下の基本宣言と列挙子。配列、複数宣言子、波括弧初期化、基本的な関数ポインターを含む |
| マクロ | オブジェクト形式および関数形式の`#define` |

関数のプロトタイプ、型の前方宣言、初期値のないファイルスコープの`extern`変数宣言、関数内のローカル変数は候補から除く。コメント、文字・文字列リテラル、C++の区切り付きraw文字列の中は探索しない。マクロ展開、`#include`の検索経路、条件付きコンパイル、名前修飾・オーバーロードによる候補の絞り込みは扱わない。プリプロセッサーの各分岐は原文どおり読むため、非アクティブな分岐の候補も含まれることがある。複雑な宣言子、演算子、Cの旧式関数定義、処理系固有の構文は検出を保証しない。

既存のファイル復号とワークスペース検索ワーカーを使う。作業領域は16 Ki UTF-16単位の読み取りバッファーと20単位の先読み、語長4,096単位、候補判定のヘッダー256トークン・16 Ki単位、深さ1,024で制限し、ファイル間で再利用する。原文外のUnicodeエスケープや分割された名前、未完の構文、上限超過、読取中の変更で確定できない場合は部分結果として扱う。走査はF12またはメニュー操作時にだけ発生し、起動・描画・常駐索引の処理は追加しない。[C++の字句仕様](https://eel.is/c++draft/lex.string)・[関数定義](https://eel.is/c++draft/dcl.fct.def.general)

## 5. 完了と候補選択

| 状態 | 表示・操作 |
| --- | --- |
| 全件評価済み、候補1件 | 共用結果パネルを開かずにその候補へ移動する |
| 全件評価済み、候補複数 | 「名前一致による宣言候補」の共用一覧を表示 |
| 全件評価済み、0件 | 「定義が見つかりません」 |
| 取消・上限・読取/解析の未評価あり | 部分結果を表示。1件でも自動移動しない。確定済み候補の明示選択は可能 |
| ルートや識別子なし | 実行せず必要条件を案内 |

「定義へジャンプ（簡易）」はコンパイラレベルの精度を保証せず、同名、オーバーロード、名前空間、継承、型推論は解決しない。未評価を含む0件は「見つからなかったが未評価あり」と表示し、完全な未検出と区別する。

### 5.1 候補一覧と移動の実装

F12と検索メニューから、選択またはCaretの識別子を抽出する。現在のワークスペースで除外・リンク規則を通過したファイルのうち、C#の本文からはC#、C/C++の本文からはCとC++のソースとヘッダーを探索する。比較は大小文字を区別した名前一致で、候補一覧に宣言名と種別、原文位置を表示する。

簡易探索は既存の検索ワーカーへファイルごとの宣言走査を渡す。候補を原文の名前範囲と宣言種別の表示を持つ共用結果へ変換し、既存の有界バッチ、確定、無効化、取消、操作世代を使う。読取や解析に失敗したファイルは未評価とし、同ファイルの仮候補を無効化する。移動時は共用の原文位置とファイルStampの検証を行う。

定義探索の開始時は、共用結果パネルの開閉状態を維持する。操作世代・表示・入力世代が一致し、全件評価済みで確定候補が1件なら直接移動する。複数候補、取消、上限、未評価ありではパネルを表示し、確定候補から明示的に移動できる。0件では未評価の有無を表示する。通常テストは単独候補でのパネルの開閉状態と原文選択、複数・部分結果の明示選択、0件、取消・後続入力、10,000件上限を確認する。実GUIプローブはF12、メニュー、Enterの経路を検証する。

## 6. 参照検索

SimpleSymbolNavigatorはIdentifierQueryの名前を、`MatchCase=true`、`WholeWord=true`、`UseRegex=false`の検索要求へ変換する。検索語の正規表現エスケープは不要で、正規表現そのものとして実行しない。

対象はルート内の全テキストファイル。宣言・コメント・文字列も含める。`@name`はnameで照合し、単語境界により`othername`等は除外する。一致位置は元本文のnameに対応し、必要に応じて補助表示で`@`も見せる。意味的な同一シンボルの参照であるとは表示しない。

### 6.1 参照検索UIの接続（2026-11-07）

通常の本文表示でShift+F12、または「検索 → 参照を検索（名前一致）」を使う。選択優先・未選択はCaretの識別子を採り、C#では`@`を比較名から除く。選択なし/不正語/フォルダなしは案内を表示し、既存の検索結果を破棄しない。抽出は現在の文書から最大8,196 UTF-16単位の窓だけを取り、境界に達した語や4,096単位超の語を短い語に切り替えない。

初期の参照入口は既存SearchPanel/Coordinatorへ同じ検索要求を渡す。MatchCase=true、WholeWord=true、UseRegex=falseを固定して開始し、共用の単一ワーカー・結果上限・取消・世代・確定/未確定と結果移動を再利用する。結果パネルには「名前一致」「宣言・コメント・文字列も含む」「意味解析は行わない」を表示する。通常検索を実行した際は通常の説明へ戻す。

UTF-8/CP932・日本語/補助平面/結合文字、条件の上書き、予約語の`@`表記、長い本文中の上限境界、原文位置への結果移動と本文不変を単体/結合で確認する。専用GUI試験は実コントロールのrouted Shift+F12、メニューClick、結果Enter、バインドされた説明・選択・フォーカスを確認する。物理キー/IME・包括的な性能受入とは区別する。

## 8. 意味解析による定義ジャンプ・参照検索

### 8.1 探索契約と構成（P5-09-01）

同名オーバーロード、別のスコープにある同名シンボル、条件付きコンパイルを識別するため、C#はRoslyn Language Server、C/C++はclangdに検索を委譲する。ユーザーが指定したローカル実行ファイルを標準入出力で呼び出す。コンパイラや索引を別プロセスに置くことで、本体のNative AOT配布と起動時の軽さを保てる。初回はサーバーの起動と解析を待つ必要があり、プロジェクト構成、SDK、ヘッダー、索引の整備状態で結果の範囲が変わる。

| 項目 | 契約 |
| --- | --- |
| 探索要求 | 操作種別、作業フォルダとその世代、要求ID、探索元の正規化パス・原文UTF-16位置・読込時のファイル情報と文書の版、選択した解析構成。選択がある場合はその開始位置を使い、名前の抽出は簡易検索で使う |
| 解析構成 | C#は選択したソリューションまたはプロジェクトとサーバーが使用するビルド構成。C/C++は選択したコンパイルデータベースと翻訳単位の条件。複数の構成がある場合は採用した構成を表示し、選択できない曖昧さは未確定として扱う |
| 参照の範囲 | 選択位置が指すシンボルの、サーバーが解析した構成内のソース参照。参照一覧は宣言を含めず、LSPへ明示する。複数箇所への解決は候補として残し、名前が同じ箇所の全文検索は簡易検索で提供する |
| 位置の検証 | LSPの位置エンコーディングに従い、同期した本文の位置を正規化済みのURIと原文範囲に変換する。取得した結果の範囲とファイルの状態を照合し、移動直前にも再確認する。サーバーが返す範囲に本文の版が含まれない場合はその事実を考慮し、更新が判明した結果を新しい本文へ流用しない |
| 結果 | 元の操作ID、移動先の正規化パス、原文範囲、検証に使ったファイル情報、現在の解析状態。0件、準備中・部分結果、対象外、通信失敗、取消を識別する。依存ソースの欠落や索引の状態を判断できない結果は部分結果とする |
| 画面の動作 | 解析範囲と位置を確認できる定義が1件のときは直接移動する。その他の移動可能な候補は共用一覧から選ぶ。範囲を確認できない結果と仮想URIの外部・生成ソースは移動を無効にする。古い操作の応答は採用しない |

設定は作業フォルダのセッション内に持つ。通常画面での自動検出と手動設定は8.7節に従う。外部サーバーへの接続やコンパイラ実行を許可するclangdのquery-driver設定は初回提供の対象外とする。Roslynの設計時ビルドは外部ツールの動作として扱い、プロジェクト由来の処理が実行され得ることを利用手順と設定画面に記載する。codeViewがソース内容を変更するLSP要求には応じない。既存のフォルダ除外規則を結果に適用し、ルート外やリンク解決後にルート外となるソースへの移動を受け付けない。外部SDK・ヘッダーは解析に必要な読取対象となり得る。

clangdの索引は、利用するコンパイルデータベースをユーザーのキャッシュ領域に用意してそこに保存する方式を検証する。コピー先でも元の翻訳単位と作業ディレクトリを指すようにし、元のコンパイルデータベースの更新を反映する。ユーザーのキャッシュ領域に置けることを確認できない構成では、索引作成を伴う設定を使う前に書込先を検証する。[clangdのコンパイル条件](https://clangd.llvm.org/design/compile-commands)・[索引](https://clangd.llvm.org/design/indexing.html)

影響範囲はNavigationの内部要求・LSP接続、Operationsの探索と資源の寿命、Presentationのフォルダ設定と状態表示、利用手順である。既存の結果一覧、件数上限、操作・ルート世代、取消、タブ移動を利用する。サーバーは8.7節の条件で起動し、フォルダの切替・閉鎖とアプリ終了に合わせて解放する。移行はC#の固定データでプロトコルを確認し、共通通信、両エンジン、原文位置、通常画面の順に接続する。[Roslyn Language Server](https://github.com/dotnet/roslyn/blob/main/src/LanguageServer/roslyn-language-server/README.md)・[LSP仕様](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/)

### 8.2 Roslynとのプロトコル確認（P5-09-02）

macOS arm64、.NET SDK 10.0.403、Roslyn Language Server 5.13.0-1.26514.10で確認した。一時フォルダにプロジェクト参照でつながる2プロジェクトを作り、`solution/open`で選択した`.slnx`を明示的に読み込む。呼び出し位置から別プロジェクトの`Run(int)`に移動し、参照検索が呼び出し2箇所を返すことを期待範囲と照合した。もう一方のオーバーロード、コメント、宣言は参照結果に含まれなかった。呼び出しの前に補助文字を置き、文字位置がUTF-16単位であることを確認した。

### 8.3 通信とプロセスの寿命（P5-09-03）

LSPのJSON-RPCは標準入出力の`Content-Length`フレームで送受信する。応答は要求IDで照合し、通信を閉じた場合は待機中の要求を終了する。フレームの上限はヘッダー8 KiB、本文32 MiBとする。取消・期限切れになった要求には`$/cancelRequest`を通知し、後から届く応答は採用しない。位置エンコーディングが省略された場合はUTF-16を使う。同期する文書のパス・版が変わった場合は、以前の文書を閉じて表示中の原文を再送する。

Operationsが現在のフォルダに対して言語ごとのセッションを所有する。セッションの登録後、最初の要求で実行ファイルを起動する。通信の切断や異常終了後は次の要求で起動し直す。フォルダを閉じるか切り替えると、進行中の要求を取り消し、`shutdown`と`exit`を送る。応答しなければプロセスツリーの終了を試みる。アプリの終了処理は解放を待つ。標準エラーを読み捨て、ソースを含むログを保存しない。各言語のプロジェクト読込と通常画面の接続はP5-09-04以降で行う。

### 8.4 C#のプロジェクト構成（P5-09-04）

選択した`.sln`と`.slnx`は`solution/open`で、`.csproj`は`project/open`で開く。単独プロジェクトの指定時は、SDKのMSBuildで`ProjectReference`を評価し、作業フォルダ内の参照プロジェクトも開く。MSBuildの評価は単一ノードで行い、評価用プロセスを再利用しない。複数のターゲットフレームワークを宣言するプロジェクトは各ターゲットの参照を評価する。読込完了を短時間待ち、Roslynが返すソースのプロジェクト構成を検索要求に指定する。部分結果では、読込中、参照関係の取得失敗、読込時の問題、解析構成を確定できない状態を表示する。

構成が複数ある場合はRoslynの既定構成名を結果に添えて部分結果とする。プロジェクトやSDKの評価失敗、読込未完了、どのプロジェクトに属するか不明なファイルも部分結果にする。外部ライブラリの定義など、通常の本文に移動できない応答を処理するのは原文位置の検証段階とする。

macOSの実Roslyn試験で、3形式からプロジェクト参照先の定義と参照を取得し、条件付きコンパイルの有効な分岐、共有ソースの複数構成、SDK不足、外部ライブラリの定義を確認した。[Roslynのプロジェクト読込](https://github.com/dotnet/roslyn/blob/main/src/LanguageServer/Microsoft.CodeAnalysis.LanguageServer/HostWorkspace/LanguageServerProjectSystem.cs)

### 8.5 CとC++のコンパイル条件（P5-09-05）

指定された`compile_commands.json`を使用する。指定がなければ作業フォルダの直下と`build`を順に調べる。作業ディレクトリとソースパスを正規化してユーザーのキャッシュへコピーし、clangdにそのコピーを渡す。コンパイル条件が変わると別のキャッシュ先を使用し、旧条件の索引から結果を取得しない。同じ条件ではアプリの再起動後も索引を再利用する。

検索の始めと終わりで索引完了の通知と、同期した版に対するエラーのない診断を確認する。コンパイルデータベースの欠落、同一ファイルに複数のコマンドがある場合、コンパイル条件を推定するヘッダー、索引途中や確認できない結果は部分結果とする。索引完了通知が示す範囲は利用したコンパイルデータベースである。[コンパイル条件](https://clangd.llvm.org/design/compile-commands)・[索引](https://clangd.llvm.org/design/indexing.html)

macOSのApple clangd 21.0.0で、CとC++の実ソース・ヘッダーをまたぐ定義と参照、マクロ変更後の別の定義、索引の保存先を確認した。macOSの`/var`のように親ディレクトリがリンクである場合は、解析対象とコンパイルデータベースを同じ正規化パスで渡す。

### 8.6 原文位置とファイル更新の確認（P5-09-06）

UTF-8・UTF-16・UTF-32単位のLSP位置と、codeViewの原文UTF-16位置を相互に変換する。CRLF・CR・LFを行境界として扱い、補助文字の途中、行末を越えた範囲、逆順・空範囲を拒否する。結果の`LocationLink`は`targetSelectionRange`を採る。既存のファイル読取で復号し、同一ファイル・同一範囲の結果をまとめる。範囲を検証できる単行の位置を共用結果へ渡す。

Windowsではドライブ文字の直後のコロンが`%3A`で表現されたファイルURIもドライブ絶対パスとして解釈する。リンク解決後にルート外となるパス、除外フォルダ、仮想URI、検索開始後に更新された移動先は候補から除き、部分結果として扱う。取得した候補は探索元と移動先のファイル情報を持つ。比較結果が変わった場合は、タブを切り替える前に移動を拒否する。読込後もファイル情報と選択テキストを確認し、確認できない旧位置で本文を選択しない。これはクライアントが把握できた更新と文字範囲の確認であり、サーバー内部の索引の版は8.2節の制約を受ける。

UTF各方式、補助文字、改行、CP932、対象外と更新済みのファイルを固定データで確認した。意味解析結果で元ファイルまたは移動先が変わった場合に元のタブを保つことも確認した。

### 8.7 通常画面への接続（P5-09-07）

フォルダの読み込みが完了したときに、直下の一覧からリンクを除いた通常ファイル候補を調べる。同梱Roslynがあり、`.sln`・`.slnx` が合わせて1件、またはソリューションがなく `.csproj` が1件なら、C#の意味解析を有効にする。既存のフォルダ一覧を再利用し、サブフォルダは追加で列挙しない。同梱物がない場合や候補を確定できない場合は簡易検索を使う。「検索」→「意味解析の設定…」でC#の対象を指定したり、C/C++を有効にしたりできる。

自動で有効にしたC#は、フォルダの表示を待たせずに、同じワークスペースのRoslynを起動してソリューションまたはプロジェクトの読込通知を送る。最初のF12・Shift+F12はその準備を待って同じサーバーを使う。準備に失敗した場合は最初の検索で再試行し、通常の検索結果で理由を表示する。フォルダの切替や「簡易検索に戻す」の操作では、準備とサーバーを停止する。プロジェクトの読み込みはプロジェクト由来の処理を実行する場合があるため、信頼できるフォルダを開く。

同梱サーバーはNative AOTの発行スクリプトで用意する。C#の依存関係は対象プロジェクトのSDKで事前に復元する。[配布物の構成](07-settings-distribution.md#言語サーバーの同梱p6-03-09)

定義・参照の要求には現在の読み取り専用文書のスナップショットを渡す。共用検索枠と結果一覧を使い、解析済みの定義が1件なら直接移動する。参照、複数の定義候補、部分結果は一覧に表示し、解析済みの0件と区別する。探索元の更新を検索前、応答の受取後、結果配信前に確認し、操作やフォルダの切り替えで採用できなくなった応答は破棄する。

### 8.8 代表ケースの軽量性（P5-09-09）

macOS 27.0.1、Apple M4、メモリ32 GB、ReleaseのGUI試験ビルドで、C#の小規模プロジェクトとC/C++の固定データを1回測定した。起動時と設定を有効にした直後に、言語サーバーの子プロセスが存在しないことを確認した。ウィンドウの`Opened`はプロセス内計測で431 msだった。

## 9. ジャンプ履歴

定義ジャンプとフォルダ検索・参照検索の結果への移動が確定した時点で、移動元と移動先のパス、文字コード指定、原文上の行・列、水平・垂直スクロール位置を記録する。記録は画面内のメモリで最大100件とし、別の作業フォルダを開くかアプリを終了すると破棄する。後戻りしてから新しくジャンプすると、そこから先の履歴は新しい経路に置き換わる。

「☰ → 移動 → 戻る／進む」では既存のタブ読込と位置復元を使う。閉じたタブは必要に応じて開き直し、変更後のファイルでは現在の本文と画面の範囲に位置を収める。開けない場合は元のタブへ戻り、履歴の位置を維持して理由を表示する。復元中に利用者が別のタブやフォルダへ移った場合は、保留中の位置復元を破棄する。通常の閲覧中に履歴の記録やファイル列挙は発生しない。

ショートカットはmacOSでは `Cmd+←` と `Cmd+→`、Windowsでは `Alt+←` と `Alt+→` の順に戻る・進むに割り当てる。
