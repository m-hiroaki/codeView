# 08 試験・性能評価

[索引](README.md) / 上位：基本設計8・11・12章、アーキテクチャ設計2.2・7.3・11章

## 1. 試験の分類と記録

| 分類 | 主な対象 | 実行条件 |
| --- | --- | --- |
| 単体 | 照合・位置・字句・JSON検証・状態採用 | 小さな固定データ、UIなし、時間や完了順を制御 |
| I/O結合 | 列挙・文字コード・リンク・更新・保存 | テスト用一時ディレクトリ。実ユーザーのソースを変更しない |
| UI結合 | タブ・検索欄・結果・読み取り専用・IME | Avaloniaの採用版に対応した試験方法と両OS実機 |
| 競合・障害 | 遅延・取消・キュー満杯・例外・後着 | 手動で完了を進められるテスト用I/Oと時刻制御 |
| 性能 | 起動・CPU・描画・検索・メモリ・GC | Release・自己完結型、固定基準機・固定データ |
| 配布・長時間 | 別PC・Gatekeeper・オフライン・8時間反復 | 実際の発行候補と配布手順 |

各結果に、試験ID、ビルド識別、データ識別、OS・CPU・RAM・ディスク、依存版、設定・予算、手順、期待値、実測値、合否、未実施理由を残す。初期の試験ランナーはNUnitで、`dotnet test codeView.slnx -c Release`を実行する。実装済みの単体・結合試験と部分的なGUI確認は[実装記録](../development-log.md)へ対応付け、未実装の試験・性能・別OSの確認を合格としない。

通常試験は[GitHub Actionsの両OS実行](../build.md#github-actionsでの通常試験)も用意する。ホステッドランナーでのビルド・単体/I/O結合の証拠と、固定基準機/実機GUI/配布物の受入を区別する。SDK・OS/アーキテクチャ・実行コミット・TRXを保存し、失敗/スキップ/取消を成功扱いにしない。

### 2.1 最小固定データの期待値

文字列はエスケープ展開後の本文とし、オフセット・列はUTF-16単位で数える。

| データ | 条件 | 期待値 |
| --- | --- | --- |
| `foo food Foo\r\nfoo` | 語foo、大小区別なし、単語単位 | 一致開始0 / 9 / 14。位置は1:1 / 1:10 / 2:1 |
| 同上 | 大小区別あり、単語単位 | 一致開始0 / 14。foodは除外 |
| `aaa` | 通常語aa | 非重複の先頭1件 |
| `a😀b\r\nが\nか\u3099` | 語b、語が、語か＋結合濁点 | bはoffset3・1:4。がはoffset6・2:1。分解表記はoffset8・3:1。正規化して同一視しない |
| 空本文 | 通常語x | 0件、本文は1行・1列 |
| `x\r\n` | 位置変換 | 第2行は空、EOFはoffset3・2:1 |
| `class C { void M() {} }` | 定義C / M | Cは1:7、Mは1:16。コメント・文字列で囲んだ別データは候補なし |

上記を1文字・1バイトずつの分割を含む複数のチャンクサイズで実行し、結果が変わらないことを確認する。表示側も同じ期待行列へ移動する。

## 3. 競合の制御試験

タイミング任せのsleepで競合を再現せず、I/O・Taskの解放点をテストが制御する。次の実行順を固定する。

1. 設定読込を保留しOpen A、Open Bを受付。設定確定後にCを投入し、A→B→Cが各1回であることを確認する。
2. 設定の待ち上限を進めて既定値確定。その後に元設定を完了し、設定・Openが再実行されないことを確認する。
3. タブAの読込を保留し、閉じて同パスを別TabIdで開く。旧文書を完了し、新タブへ採用されず解放されることを確認する。
4. 検索Aを保留しB→Cを要求。A停止前に枠が増えず、待機はCだけとなり、Aの後着バッチ・完了を採用しないことを確認する。
5. 結果キューを満杯にし取消。投入待ちが解除され、Task・処理枠が残らないことを確認する。
6. FileCommittedより後に完了Taskが見える場合と、UIドレインが遅い場合を作り、結果表示より先に正常完了としないことを確認する。
7. FileInvalidated送信前の例外・取消を注入し、未確定IDの終端情報で仮結果を無効化できることを確認する。
8. 再読込中に本文内検索・閉鎖・終了を行い、新旧のDocumentVersionやLeaseを混同しないことを確認する。

## 4. 性能用データ

### 4.1 本文

10 / 50 / 100 MiBのUTF-8とCP932を用意する。通常行、改行なし、極端な長行、全行一致、Unicode・CRLFを含む派生を作る。50 MiB×5タブを追加し、初回読込・再読込・色分け有無を分ける。100 MiBは拡張評価であり、1 GiBは代替方式の任意の限界調査とする。

C（`.c`）、C++（`.cpp`）、C/C++双方のヘッダー（`.h`）も文法評価に含める。コメント・文字列・プリプロセッサーとC++テンプレートを含む代表例で拡張子対応を確認し、長行・大容量・文法切替時の起動・描画・メモリ・解放を測る。`.h`はC++文法になることをDT-04で確認する。

### 4.2 リポジトリ

| レベル | ファイル数・対象テキスト合計 | 用途 |
| --- | --- | --- |
| L1 | 50,000・1 GiB | 必須性能評価 |
| L2 | 200,000・5 GiB | 拡張評価 |
| L3 | 1,000,000・20 GiB | 限界調査。一定メモリ内や高速な全件完走を保証しない |

総数と除外後対象数を記録する。標準データは全件検索可能な構成とし、深さ10以内の階層、直下10,000件、小・中・大容量混在を含める。生成seed、分布、文字コード比率、行長、既知の一致数・位置を固定する。リンク・除外・不正バイト・アクセス拒否は独立した派生にし、標準の速度試験と混ぜない。

ファイル作成・検数・ハッシュ確認でキャッシュが温まるため、データ準備は測定前の別工程にする。限界調査で打切った場合は走査済み規模と理由を残す。

| シナリオ | 試験内容 | 判定・記録 |

| QS-01 | プロセス開始→初回描画を両OSで10回以上 | 目標1秒以内、中央値・最大。初回署名確認と通常を分離 |

## 6. Cold / Warmと検索速度

Coldは対象データがOSファイルキャッシュにない状態を意図し、専用機での再起動後初回等の準備方法を固定する。プロセス再起動だけをColdにしない。ウイルス検査・事前走査の影響と物理I/Oを確認し、条件不明ならCold相当と明記する。日常環境のキャッシュを無断で消去しない。

Warmは同じ対象を走査した後に反復する。全量がRAMに収まらなければ部分的Warmと記録する。検索語・除外・文字コード・ビルドを統一し、通常語・正規表現を分ける。全件未一致検索で完走速度を測り、既知位置の一致・多一致上限・取消は別に測る。各Cold試験の前提を毎回準備し直す。

FileReaderの事前検証と消費読込は同じ「1回の検索」に含め、検証パスを除外して速度をよく見せない。MB/秒は論理対象バイトを分子とする値と、物理I/O量を分け、複数パスの実コストを記録する。最初の仮結果と、移動可能な確定結果までの時間も分ける。

## 7. CPU・メモリ・割当・GC

| 観測 | 詳細 |
| --- | --- |
| CPU | 起動・本文・文法・スクロール・検索の平均・ピーク、待機時の継続負荷 |
| メモリ | 管理ヒープ、プライベート・常駐メモリ、ネイティブ分、ピーク、本文サイズに対する増加 |
| 割当 | 操作単位の累計、バイト/秒、大きな文字列・配列の生成元 |
| GC | Gen0 / Gen1 / Gen2の差分回数と頻度、停止合計・最大・分布、GC時間割合 |
| LOH | 割当量・件数・生成元、保持サイズ・断片化。最終サイズだけで割当量としない |
| 資源 | ファイルハンドル／記述子、スレッド、Task、Lease、文法接続、キュー・待機要求の数 |

採用.NET版の指標とトレースの対応を確認する。[Microsoftのランタイムメトリクス資料](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/built-in-metrics-runtime)の累積値とGCイベントを使い分け、取得できない分布は未計測とする。指標によって世代別回数の意味が異なる場合は定義も記録する。

UIフレーム・入力遅延・GC停止を同じ時刻軸で突き合わせる。計測負荷の低い合格判定と詳細トレースを分ける。通常機能で強制GCを実行しない。本文閉鎖後にOSの常駐量が即減るかだけで判定せず、管理参照・ハンドルと予約領域を区別する。

## 8. 長時間・反復試験

両OSのReleaseで10分以上ウォームアップし、以降を基準にする。

- 8時間、L1でタブ切替・スクロール・全文・参照・取消・ルート切替を固定操作列で繰り返す。
- 1,000サイクル、小ファイルと50 MiBを開いて検索・切替後すべて閉じる。
- 1,000検索、完走・即時取消・上限・最新要求への置換を混ぜる。

30分ごとのCPU・メモリ・ハンドル・スレッドと、100サイクルごとに同じ空状態の資源量を記録する。本文の強参照・購読・未観測Task・文法・Leaseが増え続けず、対象を削除・置換できることを確認する。許容幅はD-09で試験前に固定する。短縮した試験は長時間試験完了と扱わない。

## 9. Phase別の完了条件

| Phase | 設計・試験上の関門 |
| --- | --- |
| 1 | SDKとUI版固定、起動・設定待ち・Open・例外境界、書込禁止の解釈、読み取り専用の確認 |
| 2 | 本文構築・UI移譲・ReadLeaseの実現性、文字コード追加I/O、GC・本文予算、第一候補の採否。未達なら代替評価へ |
| 3 | ルート・ツリー・タブ、処理枠、リンク、開閉時解放。Operations分割の兆候をレビュー |
| 4 | 検索方式・上限・Unicode・正規表現制限を確認し、全検索・Cold/Warm・競合・GC予算を検証 |
| 5 | C#基本宣言と参照、部分結果、精度の既知制限、候補選択・移動 |
| 6 | 発行形式・CPU・署名、両OS別PC・IME・Gatekeeper・オフライン、8時間と各1,000回、性能の最終回帰 |

各段階で起動・本文・ツリーの回帰を確認し、未対応は未測定として残す。性能未達のために本文モデル・依存方向等を変える場合は、理由・利点・不利点・影響範囲・移行計画を提示して承認後に実施する。
