# 長行表示の未達と表示範囲を限定する試作

状態：A-01切分け / A-02比較試作。2026-10-31。通常UIへの採用は未決定。[性能予算](performance-plan.md)・[実装記録](development-log.md)に接続する。

## 1. 確認した問題

macOS arm64、Avalonia 12.1.3 / AvaloniaEdit 12.0.0候補、文法なし、1180×800 DIP / scaling 2で実測した。

| 条件 | コア構築 | GUI接続の同期区間 | GUIでの結果 |
| --- | --- | --- | --- |
| UTF-8 50 MiB、通常改行 | 890.1ms | 89.5ms | 64回の同期ScrollTo/EnsureVisualLines最大0.64ms、tick間隔最大18.1ms |
| UTF-8 50 MiB、単一行 | 156.4ms | 約27.7秒 | スクロール継続中に停止。sampleの物理footprint表示9.3G |

コアとGUIは別プロセスの初回計測であり、差分を厳密な各内部処理の時間にはしない。GUI値も物理描画完了や入力応答の証拠ではない。ただし文法がない単一行でも接続時に時間・メモリ予算を大幅に超えることを確認できた。コードや色設定の変更だけで是正済みにはできない。

上流[VisualLineText](https://github.com/AvaloniaUI/AvaloniaEdit/blob/master/src/AvaloniaEdit/Rendering/VisualLineText.cs)は行要素の残りの文字列をTextCharactersへ渡す。[VisualLine](https://github.com/AvaloniaUI/AvaloniaEdit/blob/master/src/AvaloniaEdit/Rendering/VisualLine.cs)の長行用条件は一部要素生成の抑制であり、画面外の横方向の全文レイアウトを必ず省く保証ではない。非表示構築が速くても、表示で巨大な文字列・グリフ処理が生じると考えられる。native sampleのmanaged名は未解決なので、具体的な関数別の寄与は未確定とする。

## 2. 比較する方式

| 方式 | 利点 | 不利点・今回の評価 |
| --- | --- | --- |
| 通常のAvaloniaEditへ全文接続 | 位置・選択・コピー・文法の既存機能を使える | 通常改行は初回代理指標で予算内。単一長行は未達 |
| 表示用の有界ウィンドウ | 元本文から表示周辺だけを切り出し、1行のレイアウト量も制限できる | 元座標との変換、長行内の移動、選択・コピー・文法状態を別途正しく接続する必要がある |
| 独自の全面的な仮想テキストモデル | デコード・本文保持も制御できる | 本文構築・検索・文字コード・スナップショットまで影響が広い。今回の本文保持の初回結果だけでは必要性を確定できない |
| ストリーミング / MemoryMappedFile | 元バイトの保持・ランダム読込の選択肢になる | 長行全体をUIへ渡すままでは今回のレイアウト量は減らない。表示の有界化と組み合わせる必要があり、デコードや行索引も追加で必要 |

まず元の読み取り専用文書・不変ReadLeaseを維持し、表示だけの有界化を試す。元データを切捨てたり巨大ファイルを拒否したりする対策ではない。採用後の本文モデルの全面置換は、表示の是正結果と保持予算を見て必要な場合だけ再比較する。

## 3. 現在の試作範囲

`tests/GuiProbe/TextWindow`は最大16,384 UTF-16単位の範囲を切り出し、元オフセットとターゲットオフセットを持つ。切出しの端とターゲットがサロゲート対・CRLFを分断しないよう補正する。読み取りは元ReadLeaseから行い、全文を別文字列へ複製しない。通常ビルドには含めない。

専用GUIビルドで`CODEVIEW_GUI_WINDOWED=1`を指定した時だけ、元DocumentHandleを保持し、初回と各ScrollToで表示用TextDocumentを入れ替える。元の範囲を記録して先頭から末尾までの64箇所を移動する。元本文長と表示文字数は別に報告し、短いテキストだけを別途作った比較ではない。元範囲の切出しはGUIなしでも割当・時間を測るが、これをGUI合格には使わない。

16,384は比較試作の表示量であり、製品の行長上限・色分け閾値・最終採用値ではない。試作の画面内カーソル/行番号は元文書の操作仕様を満たすものではない。Unicodeの結合列、双方向文字、タブの開始列、文法の前行状態も今回の切出し試験だけでは保証しない。

## 4. 採用時の影響範囲と移行手順

層や依存方向は維持する。変更候補はDocumentsの表示範囲・座標変換とPresentationの接続・スクロール・選択である。Operationsの本文所有・LoadEpoch・SourceStamp・読取ビューの原文座標は維持し、Contractsへ表示ウィンドウ座標を持ち込まない。本文を分割して検索したことにせず、検索は常に元本文全域を対象にする。

移行は次の順とする。

1. 同じ50 MiB長行を専用GUIビルドで比較し、接続・64箇所移動・ピークメモリを固定予算で判定する。通常改行、10/100 MiB、UTF-16/CP932も評価する。
2. 元座標のNavigatorと表示範囲を接続し、行番号・ステータス・結果移動・EOF・スクロールバーを原文に一致させる。ウィンドウ境界のUnicode・タブ・双方向表示を検証する。
3. 選択の起点と終点を元文書に保持し、複数ウィンドウにまたがる選択、全選択、コピー、キーボード・マウス・自動スクロールを実装する。コピーは原文範囲から取得し、可視範囲だけをコピーしたことにしない。
4. 文法の状態をウィンドウの先頭で誤ってリセットしない方式、または実測に基づくプレーン表示へのフォールバックを決める。タブ切替・再読込・旧Lease・文法停止・遅延通知の寿命を検証する。
5. 元の未達条件と通常ファイル、位置・検索・コピー・文字コード・起動を回帰確認し、D-02/D-03とG2の採否を更新する。

比較で失敗した場合は試作フラグを使わず従来候補へ戻せる。現在も通常製品には影響しない。採用後の戻し方は表示Adapterの切替とし、元文書の永続形式や設定移行を追加しない。

GUI・位置・選択・コピーまで成立するまでは、表示範囲の切出しが速いだけで本方式を採用しない。失敗した元の長行条件も評価台帳に残す。

## 5. ロック解除後のネイティブ比較結果

同じ50 MiB入力をWarm条件・各3回・新プロセスで比較した。[生データと再現条件](validation-results/2026-10-31-bounded-display/README.md)を保存した。単一長行の16,384単位の有界表示は接続45.81〜45.94ms、メモリ増分331.80〜338.31 MiBで、接続100ms・メモリ512 MiBの予算内。ただし同期移動の最大42.08〜44.91ms、tick間隔の最大51.55〜53.17msで60fps目標は未達である。物理描画/入力の測定ではない。

通常改行の有界表示は接続7.64〜7.86ms、同期移動最大7.80〜11.66ms、メモリ増分336.36〜341.52 MiB。一方、通常改行の全文表示は接続88.58〜91.31ms、同期移動最大0.65〜0.76msと速いが、サンプルピーク増分499.58〜513.75 MiBで1回が予算を超過した。1章の初回良好値だけで本文採用を確定しない。

有界化は継続評価するが、通常改行を一律に置換する根拠にはしない。表示量・表示文書再利用の比較、本文の保持ピークとGCの切分けを続け、4章の原文座標/選択/コピーとの統合前に通常UIへ採用しない。全文長行の既知の未達は再実行していない。G2/A-02は未完了のままとする。

## 6. 表示量とGCの比較・統合試作への判断

[1,024 / 4,096 / 16,384単位を各3回測定](validation-results/2026-10-31-window-sizes/README.md)した。1,024単位は接続10.12〜11.12ms・同期移動最大10.13〜15.87ms・tick中央値約16.66ms・メモリ増分279.36〜293.78 MiB。16,384単位はtick中央値約33.3ms、割当約535〜537 MiBで、1,024単位の約273 MiBより負荷が大きい。同一版の9回すべてで原文先頭〜EOFの64回移動、表示量上限、入力中断なし、Closed通知と終了コード0を検証した。最大tickは1,024単位でも17.01〜20.54msなので、物理描画/入力や60fpsを合格にはしない。

次の長行統合試作は1,024単位を出発点とし、4,096単位も可視幅/Unicodeの比較に残す。製品の閾値や総文字数制限を確定したものではない。通常行を含む画面の可視行数を満たす表示モデルを別途成立させる。原文座標のNavigatorと表示AdapterをDocuments内で接続し、Operations/検索の原文座標と本文所有は維持する。通常改行を一律の小窓へ置換する設計にはしない。

比較中に選択/スクロールの再帰によるStack overflowと、結果出力後の終了待ちを各1回確認した。元ログ/サンプルを残し、正式値から除外した。自動計測への入力混入の検知/中断と描画コールバック外への終了要求は計測器だけに加えた対策で、製品の選択障害を解消した証拠ではない。統合時には、選択中の範囲入替・自動スクロール・キャレット可視化の再入を制御し、マウスボタン解放/キャプチャ喪失、タブ切替/再読込を含む実機受入へ加える。遷移中に選択を失う回避策や、入力を禁止して合格にする対応は採用しない。

## 7. 原文の位置・選択・コピー基盤

Documents内にDocumentDisplaySessionを実装し、原文Anchor/Caretを表示Sliceと独立に保持する。Sliceは原文先頭のOffset/行列を持ち、同値の旧Sliceを含む遅延イベントをインスタンス同一性で拒否する。BeginCopyが原文選択と独立ReadLeaseを固定し、表示/本文ハンドルを解放した後も最大16 Ki単位のバッファで元の範囲を逐次出力できる。詳細な理由・利点/不利点・影響/移行順は[詳細設計04の6.2](detailed-design/04-documents-tabs.md)を参照する。

[単体/性能・専用GUIの接続記録](validation-results/2026-10-31-source-display/README.md)を保存した。通常単体477件合格。50 MiBの長行/通常UTF-8/CP932はコピー用Lease取得200 bytes、全文コピー約41〜49ms・872 bytes・コピー後Lease 0で、全文中間文字列を生成しない予算を満たした。出力先は数値加算するTextWriterであり、OSクリップボードの最終文字列や物理入力は未測定。

専用GUIの切出し経路もこのモデルへ変更し、長行の64箇所移動後の原文Caret/全選択状態とClosed/終了コード0を確認した。ただし画面の選択表示/マウス/キー/行番号/クリップボードへの接続は未完了で、従来の選択再帰障害を解消したことにはしない。通常UIは従来候補を維持し、G2/A-02全体は未完了である。
