# 行別投影の文字幅・Unicode文脈の比較

A-03承認済み試作のA-04-03の評価。通常UI/本文保持/検索/コピー/データ構造は変更せず、まず行別投影が全文の小さな対照と同じ文字配置を保てるか測る。受入条件を以下で固定し、差のあるケースを入力から外さない。

## 比較条件

同じネイティブWindow内の2つのAvaloniaEditに、同じフォント宣言（Menlo/Consolas/monospace）、14 DIP、LTR、タブ幅4、折返しなしを設定する。全文対照は4,096 UTF-16単位未満の単一段落だけ。投影側は既存DocumentRowProjectionを使い、指定原文Offsetと列数の短い表示を作る。全文の巨大行レイアウトを再導入する候補ではない。

12固定ケースはASCIIの途中切出しとUnicode全文一致の対照2件、タブ位相、結合文字の左右切詰め、ZWJ絵文字の左右切詰め、国旗RI、Hangul Jamo、Indic結合列、Bidi埋込み、Arabic連結である。固定入力の単体3ケースで、スカラーの途中を切らないこと、全位置往復と原文コピー、既知の結合境界分断が実際に含まれることを確認する。

各スカラー境界で、全文側の原文位置と投影側の対応位置をTextView.GetVisualPositionで取得し、それぞれの切出し先頭からの相対X/Yを比較する。最大差0.1 DIP以内を配置一致とする。元の小さな全文についてStringInfo.ParseCombiningCharactersが返す境界に、投影の左右端があるかも記録する。SourceMapping/原文コピーは完全一致を必須とする。Native GetPositionによるヒットも記録するが、ゼロ幅文字/Bidiでは複数位置が同じ座標を持つため、単純なoffset一致を視覚正確性の合格条件にしない。

対照2件は配置/境界とも一致を必須とする。各ケースの受入は左右の結合境界が保たれ、配置差も閾値内であること。全ケースが受入になるまで比較全体のAcceptedをtrueにしない。スカラー位置が正しいことだけで、結合列/文字幅まで正しいとは扱わない。

## 取得と受入の分離

専用ビルドでCODEVIEW_GUI_ROW_VISUAL_CHECKS=1を指定し、入力なしの使い捨てCIでだけ比較を実行する。通常の行別操作/読取専用/検索パネル試験と同時に動かさない。両OSで独立3プロセスを直列に実行し、各12ケースの生位置、境界、原文ハッシュ、差と採否を保存する。

収集成功はAcquired=trueであり、投影の採用可能性はAcceptedで別に示す。対照や原文対応の破壊、非有限値、未取得/Timeout/入力割込みはワークフロー失敗にする。一方、正しく取得できた未達ケースはAccepted=falseとして保持し、比較取得の成功をG2合格としない。

Unicode全文対照、タブ、結合文字左端、Bidiの4ケースでControlを96 DPIのPNGへ描画する。これはControl.Renderの記録であり、物理ディスプレイの描画完了やOSスクリーンショットではない。ネイティブ描画倍率とフォント宣言も残すが、実際の全フォールバック書体の同定や全DPI/フォントの受入ではない。PNGは文字列選択によるスタイル分割を加えずに保存する。

使用APIは導入済みAvaloniaEdit 12.0.0の[固定コミットのTextView](https://github.com/AvaloniaUI/AvaloniaEdit/blob/86fdebec4cff7affb0e14c7885df71d28edce777/src/AvaloniaEdit/Rendering/TextView.cs)を確認した。メソッド自体は表示文書の位置を使うため、比較では必ず元の原文位置を投影へ変換してから呼ぶ。

## コストと残課題

通常製品の描画/本文/索引は変更しない。専用CIでは小さな2つのControlとPNG保存の負荷が加わり、CPU/割当/メモリはこの比較処理全体を含む。CaseControlMillisecondsもPNGのFrame待ち/保存を含み、純粋な表示レイアウト時間ではない。巨大行の非表示prefixを測る方式、文字素/Bidi/タブ文脈の是正、物理入力/描画、文法、大規模固定予算の合格はこの比較で完了扱いにしない。
