# Unicode文脈と有界描画の追加設計案

状態：2026-11-06承認済み。ユーザーから「設計案に沿って専用試作を進める」と回答を受けた。以下の上限/既定OFF/移行/受入を維持して実装検証へ進む。通常UIへの採用や既存予算の緩和を、この承認から推定しない。

## 理由

[両OSの比較](validation-results/2026-11-06-row-visual/README.md)で、原文のUTF-16位置とコピーは一致したが、12ケース中8件で結合境界/Arabic連結が未達だった。サロゲートの保護だけでは、結合文字・ZWJ・国旗RI・Jamo・Indicのまとまりを維持できない。Arabicは文字素境界を合わせるだけでも前後の字形連結が残る。

既存A-03は「全文分の一覧/索引を追加しない」行別投影であり、別レンダラーへの全面置換も選んでいない。ここで追加する文脈チェックポイントと、文脈を配置して必要範囲だけ描くControlはデータ構造/描画責務の変更になる。[AGENTS.md](../AGENTS.md)の「承認なしに実施しないこと」に従って実装前に追加確認し、上記の範囲で承認を受けた。

## 比較した選択肢

| 方式 | 利点 | 不利点・判断 |
| --- | --- | --- |
| 各スクロールで行頭から文脈を走査 | 本文以外の索引を不要にできる | 巨大prefixほどUI処理が増えるため不採用 |
| 全文/全文字素一覧を別文字列・配列へ複製 | 全体の位置を求めやすい | 本文長比例の追加保持/巨大行レイアウトを再導入するため不採用 |
| 固定長だけ前後を足す | 小さく実装できる | 長い結合列・RIの偶奇・Bidi状態等で正しさを保証できず、これだけで受入としない |
| ワーカーの疎な文脈チェックポイント＋可視範囲の文脈付き描画 | 巨大prefixのUI全走査を避けて原文契約を維持できる可能性 | Unicode状態/予算/寿命と入力・描画の再検証が必要。下記の範囲で試作する案 |

## 承認を求める専用試作

1. Documentsの任意機能として、既存の読込/構築ワーカーでUnicode文脈の疎なチェックポイントを作る。本文は既存の不変Rope/ReadLeaseを使い、別の全文文字列を作らない。位置は原文の64bit UTF-16 Offsetとする。
2. チェックポイントは文字素分割の再開状態と既知境界、前後文脈を得るための位置を持つ。不変スナップショットをHandle/表示セッションの世代へ結びつける。文字ごとの一覧ではなく、一定間隔と明示した上限内の例外記録に限る。最初の比較候補は約4 Ki UTF-16間隔、索引合計1 MiB/本文以下。最終密度は構築/再開コストを測って決め、予算内と未測定のまま断定しない。
3. 分割は.NET StringInfoの結果を対照とし、再開可能な公開APIで実現できなければ、Unicodeの公式データ/規則を固定版で用いる小さな実装をDocuments内で評価する。新しいフレームワークは導入しない。公式適合データ、ライセンス、使用版、チャンク/再開境界を記録する。
4. 行別投影へ「表示したい原文範囲」と「前後文脈を含む取得範囲」を区別する不変メタデータを追加する。文脈は原文のままで、NFC正規化や人工の本文文字へ置き換えない。コピーと検索は従来の原文範囲だけを使う。
5. 専用フラグ内で既存Avaloniaの文字配置APIを使う行描画Controlを試す。文脈を含む短い区間を配置し、必要な範囲だけをクリップして描く。前後文字を単に透明な文字列へ置換して字形連結を失わない。選択背景/Caret/ヒットテストを同じ配置結果から原文へ戻し、既存の単一入力受付・コピーCoordinatorへ接続する。
6. 通常UI・従来の連続Slice・現在の行別方式は比較用に維持する。索引の収集と新しいControlは既定OFF。外部公開API、レイヤ/プロジェクト/依存方向、TabState、元本文/検索/コピー、ファイル形式、設定の保存は変更しない。

## 上限と未達の扱い

現在の可視投影16 Ki UTF-16単位と取得50 ms/64取得4 MiB、接続100 ms、tick16.7 ms等の既存条件を基準として残す。文脈を含める候補は別に測り、最初は1投影の文脈取得合計64 Ki UTF-16以下、索引1 MiB/本文以下、配置キャッシュ4 MiB/アクティブView以下を実験上限とする。これは既存予算を緩和した合格条件ではない。追加保持、構築CPU/取消応答、再開量、UI割当、ネイティブ保持を別々に記録する。

単一の結合列が上限を超える、解析状態/配置文脈が確定できない、キャッシュが足りない等のケースは黙って切らず未達として残す。入力を試験から除外して合格にしない。巨大結合列や長いBidi段落をこの案で解決済みとは主張しない。上限内での是正が成立しなければ、代替を提示してG2未完了のまま戻す。

## メリット・デメリット

メリットは原文位置/コピーを維持したまま、UI上の巨大prefix走査と全文レイアウトを避けられる可能性があること。通常表示へ負荷を加えず、現在の8未達を同じ対照で検証できる。

デメリットはワーカーの追加走査/索引保持とUnicode版追従、文脈取得と配置の複雑化、新しい描画Controlのフォント/選択/ヒットテスト/アクセシビリティ/DPI検証が必要なこと。CPU/メモリ/起動が悪化する可能性があり、採用できるとは未確定である。既存Avaloniaを使っても、これらの責務が自動的に解消するとは扱わない。

## 影響と寿命

| 対象 | 変更と検証 |
| --- | --- |
| Builder/Handle | 任意のワーカー収集、取消・失敗時破棄、不変索引と本文版の一致 |
| 表示セッション/投影 | 文脈/可視範囲の原文対応、古い索引/別本文/範囲外の拒否 |
| 専用Control | 文脈付き配置、クリップ、選択/Caret/ヒット、フォント/DPI/アクセシビリティ |
| 切替/再読込/終了 | 現在の表示だけが配置を所有し、旧配置/購読/キャッシュを破棄。コピーLeaseは原文だけを借用 |
| 通常UI/Operations/設定 | 既存契約と既定OFFを維持し、追加の全行/全文走査を行わない |
| 文法 | 原文の行状態と文脈/可視位置を混同せず、後続の文法あり評価へ接続 |

## 移行計画と戻し方

承認後、まずワーカー索引/再開の単体とメモリ・CPU比較を作る。次に別フラグのControlで小さな全文対照12ケースと、長い結合列/RI/Arabic/Bidi/改行/チャンク境界を比較する。原文の全選択/逆方向選択/コピーとタブ/再読込/検索/終了を現行の統合試験で再実行する。その後10/50/100 MiB・50 MiB×5・文法有無・両OSの固定予算、物理入力/描画・DPIを確認して採否を判断する。

既定OFFなので比較フラグを外せば現在の試作へ戻る。元本文/設定の保存形式とタブ/検索の契約を維持し、データ移行は不要。G2の通常採用はこの承認から推定せず、未達の記録を消さない。
