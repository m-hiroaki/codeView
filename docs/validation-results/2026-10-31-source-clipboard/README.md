# 原文コピー受付・最終文字列・OSクリップボード接続

2026-10-31。`f675d87`からの差分。有界表示の通常UI採用は未完了。今回はコピー処理の所有者と、専用GUI試作のクリップボード接続を検証した。

## 変更と所有

OperationsのClipboardCopyCoordinatorが、原文選択を固定したDocumentSelectionCopyを引き受ける。準備/OS書込みを含む実行は1件、待機は最新1件。新しい原文コピー要求は古い要求を取消し、置換された待機は即時完了/Lease解放する。取消不能なOS書込みは実終了まで枠を保持し、その後に最新要求を実行する。原文のタブ/表示を切り替えたら、まだ書込みを始めていない処理を不採用にする。

選択/キャレットの変更だけでは押下時点のコピー範囲を変えない。空選択はクリップボードを変更せず、進行中のコピーも置換しない。OS書込み開始後の取消は既存の書込みを元へ戻せないため、結果にWriteStartedを保持する。この受付が直列化するのは同じ所有者への原文コピー要求であり、他のアプリや別のUI経路のクリップボード変更を監視/排他するものではない。

ReadRangeAsStringは最終stringの領域を1つ作り、最大16 Ki単位のバッファで元の範囲を埋める。バッファは消去して返し、全文サイズのStringBuilder/中間文字列を作らない。Snapshotは準備終了後、OS呼出し前に解放する。完了した要求/Taskへ本文を結果として保持しない。未知例外や無関係な取消は受付を停止し、待機を実行せず、要求TaskとPendingWorkへ失敗を伝える。

専用GUIは初回コピー時だけ所有者を作り、UIでSetValueAsync(DataFormat.Text)/FlushAsyncを呼ぶ。利用不能なサービス/既知のOS可用性エラーは再試行可能な状態として表示し、SEHを含む未知障害は致命的経路へ渡す。文書切替/閉鎖時に無効化し、単一の通知監視Taskで最新要求だけを表示する。終了時はコピー処理も既存の最大2秒の待機へ含める。2秒を超える取消不能OS処理の完了や、開始済み書込みのロールバックを保証しない。

## 通常単体試験

Release通常558件合格、失敗0・スキップ0（`clipboard-copy-all-final.trx`）。追加22件は受付/寿命15件、文字列4件、コピーキー3件。

- A準備中にB→Cを要求してB未実行/即時解放、A終了後だけCを書込む。
- OS書込みを保留し、次の準備/書込みが重ならないことと、最終書込み順を確認。
- 選択変更/元本文・表示の閉鎖後も押下時点の文字列を保持。文書無効化/終了は準備/待機を取消し、実ワーカー/OS処理の終了までPendingWorkが完了しない。
- 空選択の非変更、利用不能後の再試行、誤った長さ、未知の準備/書込み/SEH、無関係な取消、旧Taskの失敗観測、拒否時の所有、別スレッドを検証。
- 日本語/補助平面文字/CRLF/結合文字を原文のまま保持。空/EOF/不正範囲/取消/破棄済みを検証。
- 所有者と元本文を保持したままでも、完了したコピー文字列を回収できることを弱参照で確認。強制GCはこの試験内だけで使う。

## 50 MiBの文字列準備性能

同じ生成済み50 MiBの長行/通常UTF-8/CP932を各1回、新しいテストプロセスで順次測定した。macOS arm64 / .NET 10.0.12 / Release。ビルドを並走させていない。表示/元ハンドルを閉じてから文字列を作り、原文の全UTF-16単位数と事前走査の加算チェックサムを照合した。内容/順序の完全比較は通常単体試験で行う。

| 入力 | 原文UTF-16単位 | 準備 ms | CPU ms | 当該スレッド割当 bytes |
| --- | ---: | ---: | ---: | ---: |
| UTF-8 単一長行 | 39,945,760 | 12.490 | 13.015 | 79,892,312 |
| UTF-8 通常改行 | 30,980,684 | 11.117 | 11.654 | 61,962,160 |
| CP932 通常改行 | 38,947,124 | 12.685 | 13.193 | 77,895,040 |

各割当は最終文字列のUTF-16本体2×単位数＋792 bytes。GC停止/Gen0/1/2はすべて0、コピーLeaseはすべて0へ解放。事前の[性能予算21章](../../performance-plan.md#21-クリップボード用の最終文字列)に3件合格した。元本文読込でプール利用済みの条件。これはメモリ上の準備で、旧ストリームコピー872 bytesとは処理内容が異なる。OS転送/Flush/追加複製/常駐保持・OSメモリ・個別停止・物理入力遅延は測っていない。大きな最終文字列そのものの割当は残る。

再現はCODEVIEW_PERF_CLIPBOARD_FILEに生成済み入力を指定し、`dotnet test codeView.slnx -c Release --no-build --filter FullyQualifiedName~ClipboardStringPerformanceTests`を実行する。JSONは`clipboard-string-*.json`へ保存した。

## macOS実機のOS転送

Macの再ロックを確認して解除を依頼し、ユーザーの解除連絡後に実行した。前回と同じ生成済み10,435 bytes・8,033 UTF-16単位・5行、長行は8,008単位。専用GUIは最大1,024単位の表示を維持し、次を実キーでコピーした。

1. 先頭行の2単位`ir`。同アプリの検索欄へOS経由で貼付し、実値`ir`を確認。
2. 原文の全8,033単位。表示窓の1,024単位だけではないことを確認。
3. 長行を逆方向に選択した8,008単位。成功表示と原文位置を確認。

検証モードのOS読戻しを3回行い、渡した最終文字列とのOrdinal一致3回、不一致0回。読戻し文字列そのものはログへ残さず、件数/一致結果だけを保存した。[画面](source-copy.png)、[AX](source-copy.ax.txt)、[報告](source-clipboard-20261031.json)、[ログ](source-clipboard-20261031.log)を保存し、Closed/CLI終了コード0を確認した。原文ファイルのハッシュも一致した。これは小さい入力のmacOS試験で、Windows転送、アプリ終了後の保持、大容量OS転送、OS書込み途中の実機取消/競合負荷、長時間利用の合格ではない。

専用ビルドにCODEVIEW_GUI_WINDOWED=1 / CODEVIEW_GUI_INTERACTIVE=1 / CODEVIEW_GUI_VERIFY_CLIPBOARD=1を指定し、生成フォルダと本文ファイルをCLI引数で渡す。VERIFYはテスト用の追加読戻しで、通常は無効。実クリップボードを変更する試験であり、読戻しの追加文字列もOS転送性能へ混ぜない。

入力を再生成する場合は、存在しない出力先へ次の内容をUTF-8で保存する（末尾空行を含む）。

```python
lines = ["// first", "// " + "sample = 123; 注文😀; " * 400 + "END😀", "x", "// last line", ""]
body = "\n".join(lines).encode("utf-8")
```

ハッシュは[input-manifest.json](input-manifest.json)、[ソース/アセンブリ情報](provenance.json)を参照。実機後に可用性エラーの条件からSEHExceptionを明示除外し、未知SEHの単体試験と最終GUIビルドのコンパイルを追加確認した。実機の成功経路は同じだが、更新前の実機DLLと更新後のコンパイル確認DLLを混同しない。
