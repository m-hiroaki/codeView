# 長行の表示量とGC負荷の比較

2026-10-31。前回の[16,384単位の比較](../2026-10-31-bounded-display/README.md)を受け、同じ50 MiB単一長行を1,024 / 4,096 / 16,384 UTF-16単位で比較した。通常製品への採用は未決定。G2/A-02は未完了。

## 条件と測定範囲

macOS 27.0.1 arm64、32 GiB、.NET 10.0.12、Avalonia 12.1.3 / AvaloniaEdit 12.0.0、文法なし、1180×800 DIP、scaling 2。生成済みUTF-8 50 MiB・39,945,760 UTF-16単位・単一行を保持したまま、最大表示量だけを変えた。入力は事前全読込によるWarm条件。各3回、新プロセス、順次実行し、ビルド/単体試験は並走させていない。他のユーザーアプリは稼働しており、専用OS環境ではない。

[性能手順](../../performance-plan.md#8-長行の有界表示試作)の専用ビルドに`CODEVIEW_GUI_WINDOWED=1`、`CODEVIEW_GUI_WINDOW_CHARS=1024` / `4096` / `16384`を指定する。`CODEVIEW_GUI_PERF_REPORT`には未使用の絶対パスを指定する。通常製品ビルドには計測器・表示量指定を含めない。

正式9回はすべて原文先頭からEOFまで64回移動し、表示量上限、移動記録65個（初回接続を含む）、入力による中断なし、Closed通知、終了コード0を検証した。原文を縮めた比較ではない。生JSON/ログ・[summary.json](summary.json)・[ソース/入力/DLLハッシュ](provenance.json)を保存した。

数値は各3回の範囲。tickはRequestAnimationFrameのコールバック間隔であり、物理描画完了や物理入力応答ではない。

メモリは10ms間隔のphys_footprintサンプルピークの基盤からの増分。割当/GCは計測器構築から報告生成前までで、読込・表示文書生成・64回移動・計測器自身を含む。プロセスCPUはこれより広い起動からの累積である。GC停止合計を単一の停止時間と解釈しない。単体読込のみの150ms予算を64回移動込みの区間へ転用しない。LOHの直近GC後サイズはJSONに残すが、LOH割当量・ピーク・個々の停止は未トレースである。強制GCはしていない。

接続100ms・メモリ512 MiBは全条件で満たした。1,024/4,096単位では更新間隔の中央値が約16.7msとなり、長行の表示量が負荷へ影響することを確認した。ただし最大値やp95は16.7msを超えるため、物理画面の60fps保証や入力応答の合格とはしない。表示する情報量の減少とのトレードオフもある。

## 比較中の失敗と計測器の修正

1. 最初の1,024単位試験はscroll-9付近でStack overflow、子プロセス終了-6、報告JSONなし。[圧縮した元ログ](long50-size1024-20261031-1.log.gz)を残した。スタックはSelectionMouseHandlerのスクロール変更→選択拡張→Caret.BringCaretToViewを再帰している。上流の[12.0.0ソース](https://github.com/AvaloniaUI/AvaloniaEdit/blob/12.0.0/src/AvaloniaEdit/Editing/SelectionMouseHandler.cs#L652)では選択モード時にこの経路へ入るが、今回のモード遷移や物理操作の有無は記録がなく未確定。外部入力が原因だと断定しない。製品の選択障害を直したことにはしない。
2. 自動測定中のキー/クリック/ホイールは、計測器のTunnelハンドラーで検知して処理を止め、`Failure=physical-input-during-probe`・終了コード1で中断するよう変更した。これは自動比較の条件維持であり、製品で入力を禁止する対策ではない。この中断経路の意図した物理操作試験は未実施。正式9回で中断なしと確認しただけで、クラッシュの再現条件が解消したとは判定しない。
3. 次の試験はcompleteとJSONを出力したがプロセス65969が継続。GUI取得はタイムアウトした。[同プロセスのsample](long50-size1024-guarded-20261031-1.sample.txt.gz)はmain threadがAppKitのイベント待ちであった。計測値は[incomplete-shutdown.json](incomplete-shutdown.json)として別保存し、正式値から除外した。観測後にSIGTERMで終了し、再起動を重ねてはいない。原因箇所はmanagedスタック未解決のため確定していない。
4. 計測器が描画コールバック内から直接Closeしていたため、通常の終了要求をDispatcherへPostし、そのコールバックを抜けてから行うよう変更した。Closing/Closedをログへ加えた。単発確認と正式9回でClosed・終了コード0を確認した。製品の終了処理自体は変更していない。

## 判断と次の実装

長行のレイアウト上限として1,024単位を次の統合試作の出発点とする。最終閾値・製品設定・原文の行長上限を決定したわけではない。4,096単位も通常文字/タブ/Unicodeと可視幅の検証に残す。通常改行は元の全文表示の移動が速いため、一律に1,024単位へ切り替えない。

単純な総文字数の小窓では、短い行が多数ある画面の可視行を満たせないことがある。通常行/長行を区別する表示方式、原文の行列・選択・コピー・スクロールバー・タブ保存位置との統合が必要である。選択中の表示範囲入替は今回の再帰を含めて受入条件へ追加する。未対応の結合列/双方向文字/タブ/文法状態や10/100 MiB・別文字コード・Windowsも残る。

通常製品ビルドの単体464件合格（失敗0・スキップ0）。追加20件で表示量指定の正常/不正/上下限と1,024/4,096単位での先頭/中間/EOFの原文一致・座標変換を検証した。計測器固有のnative終了/入力は単体試験だけで証明せず、上記の実行結果と未検証事項を区別する。
