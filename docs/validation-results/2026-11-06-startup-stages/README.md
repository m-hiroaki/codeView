# 起動12段階の切り分け

A-01-03。`94bbefdf1582b63940f9303ab3abac076c480a07`の[両OS実GUI CI](https://github.com/m-hiroaki/codeView/actions/runs/42196544549)で、空画面/日本語小ファイル各10回、合計40独立プロセス/480時刻を取得した。[指標の定義](../../native-gui-validation.md#起動段階の切り分け)。変更は明示診断の時刻記録と検証に限り、通常製品の起動式は従来どおり、全チェックポイントと型はコンパイル対象外である。層・依存・公開API・製品データ構造は変更していない。

## 区間の結果

各セルは空画面 / ファイル指定の中央値（ms）。同じ入力でも各起動は別プロセスである。

| 隣接する計測点の区間 | Windows | macOS |
| --- | ---: | ---: |
| builder-configured → app-initialize-start | 185.611 / 184.797 | 256.590 / 251.437 |
| app-initialize-start → app-initialize-end | 56.485 / 56.622 | 79.467 / 85.504 |
| framework-start → window-constructor-start | 98.762 / 97.815 | 150.380 / 135.003 |
| window-constructor-start → window-xaml-loaded | **365.433 / 363.119** | **358.715 / 353.937** |
| probe-attach-start → probe-attach-end | 6.682 / 6.649 | 5.950 / 6.964 |
| framework-end → window-opened | 195.403 / 192.964 | 180.557 / 197.951 |

両OS/両シナリオでウィンドウXAML読込が最大の区間だった。計測器Attachはこの区間へ混ぜず別に取得した。全11区間の個々の値/中央値/最大は`summary.json`へ保存した。各プロセスでは全区間の和がMain→Openedと一致する。区間ごとの中央値を加算して全体中央値へ代用はしない。

XAML区間はコントロール生成等を含むが、個々の関数のCPUやJITを切り分けた値ではない。特に呼出し先へ入る前のJITは直前区間へ入る。UI基盤区間もネイティブ初期化・型初期化などをまとめて含み、単一処理の原因へ断定しない。

## 予算と回帰

| Windows | 968.236 / 1,745.401 | 962.655 / 987.935 |

本文接続はWindows中央値23.166/最大187.321 ms、macOS中央値26.035/最大31.659 ms。Windowsの接続100 ms予算と起動1秒超、Macの起動未達は残る。全体CPUはWindows空/ファイル中央値1,304.688/1,718.750 ms、Macは1,319.338/1,829.510 msで、スクロール/終了も含む。採取OSメモリの絶対ピークも各レポートと集計へ残した。Main以前のランタイム起動、物理描画/入力時刻は未測定である。

Macは以前の別ホストの取得より遅いが、同一ホストでの計測前対照がないため、時刻追加の負荷や製品の退行へ帰属させない。通常製品に処理を追加しないことはソースの条件分岐と型の除外試験で確認した。診断ビルドでの時刻記録/少量割当の負荷は、Attach区間だけから推定しない。

[通常CI](https://github.com/m-hiroaki/codeView/actions/runs/42196543620)はmacOS .NET703/Python82成功、Windows .NET700成功+既存Darwin専用3スキップ、Python62成功+既存POSIX専用20スキップ。追加5ケースで有界保持/独立スナップショット/時刻・順序境界、収集器9ケースで欠落/重複/逆行/非数値・最終Opened不一致等を確認した。手元でも通常.NET703/Python82成功、明示診断ビルドは警告/エラー0。

実GUIの読取専用は両OS各216操作、起動は各20プロセスが成功。通常製品の[Windows AOT発行/起動](https://github.com/m-hiroaki/codeView/actions/runs/42196541660)も成功し、可視ウィンドウ・終了0・生成入力SHA不変を再照合した。

## 次に比較する変更

通常起動時に非表示の検索パネルもMainWindowのXAMLで構築しているため、そのコントロール群を初回表示時だけ構築する候補を先に比較する。層・依存・検索/本文モデルは変えず、機能や性能条件を削らない。現時点で採用はしない。

比較は同一ホスト・SDK・同じ診断設定で変更前/候補を交互に各条件10回以上、空/ファイルと初回検索パネル表示を分けて行う。起動のCPU/割当/OSメモリ・各区間に加え、初回表示へ移した同期処理とレイアウト通知を記録し、100 ms予算を維持する。起動だけを速くして検索操作を重くした候補を合格にしない。名前スコープ・条件のBinding・検索語/選択肢の保持・表示/非表示の反復・結果移動のフォーカスを実GUIで回帰する。効果がない/操作予算に違反する場合は候補を戻す。
